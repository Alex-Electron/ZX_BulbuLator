# 1. GENERAL SOUND

## 1.1 Что это за устройство

Отдельный микропроцессорный комплекс на шине Спектрума: свой Z80 на 12 МГц без тактов ожидания,
32 КБ ПЗУ (27256), 128 КБ статического ОЗУ в базовой версии (из них 112 КБ доступно модулям и
сэмплам), прерывание 37.5 кГц, четыре независимых 8-битных канала с 6-битной громкостью на каждом
(`GSPROG` §1, стр. текста 132-136). Каналы 0 и 1 — левые, 2 и 3 — правые (`GSPROG` §2, стр. 174).

Программирование сводится к передаче байт модуля/сэмплов и подаче команд «играть», «громкость»,
«стоп» — интерпретацией модуля занимается прошивка самой карты (`GSPROG` §2, стр. 155-159).

## 1.2 Порты со стороны Спектрума

Со стороны машины карта — четыре регистра на двух адресах (`GSPROG` §3, стр. 176-195):

| Порт | Направление | Что это |
|---|---|---|
| `#BB` (187) | запись | **Command register** — регистр команд |
| `#BB` (187) | чтение | **Status register** — слово состояния |
| `#B3` (179) | запись | **Data register** — данные от Спектрума карте |
| `#B3` (179) | чтение | **Output register** — данные от карты Спектруму |

Ключевое: регистр данных и регистр вывода лежат по одному адресу и трогают один и тот же бит
состояния, но это **два независимых регистра**; значение, записанное в один, остаётся в нём до
следующей записи (`GSPROG` §3, стр. 204-207).

`NGSPORT` подтверждает то же самое как определения для ассемблера:
`GSCOM EQU #BB` (write-only), `GSSTAT equ #BB` (read-only), `GSDAT EQU #B3` (read-write).

### Дешифрация адреса — здесь источники расходятся

* `ZXMS` (живое железо): `wire port_b3 = zxa[7:0] == 8'hB3` и `port_bb = zxa[7:0] == 8'hBB`
  (`cpld/rtl/top.v:182-183`) — **полный 8-битный** декодер.
* `UNREAL` (эмулятор): `if ((port & 0xF7) == 0xB3 && conf.gs_type)` (`io.cpp:92` на чтении,
  `io.cpp:987` на записи) — то есть **A3 из дешифрации выброшен**, `#B3` и `#BB` различаются
  только им, а `#F3`/`#FB` и т. п. туда же не попадают (A2,A1,A0 = 011 остаются в маске 0xF7).
* `MISTGS` получает готовый `CS_n` снаружи и различает регистры одним входом `A` (`gs.v:75, 94`).

**Расхождение:** UnrealSpeccy отзовётся на порты, которых настоящая карта не декодирует. Для нас
безопаснее эталон `ZXMS` — полный 8-битный декодер, и он же у нас (`sources/atlas_core/main.v:515-516`).

## 1.3 Слово состояния — смысл КАЖДОГО бита

```
 бит 7 — Data bit    (флаг данных)
 биты 6..1 — НЕ ОПРЕДЕЛЕНЫ
 бит 0 — Command bit (флаг команд)
```
(`GSPROG` §3, стр. 179-190; `NGSINFO` стр. 68-71 слово в слово: «D7 - data bit, D6..D1 - не
определены, D0 - command bit»; `NGSPORT`: `B_CBIT equ 0 / M_CBIT equ 1`, `B_DBIT equ 7 / M_DBIT equ #80`.)

Правила изменения флагов (`GSPROG` §3, стр. 196-203) — это и есть весь протокол:

* **Command bit** устанавливается **аппаратно** при записи в `#BB`. **Сбросить его может только
  сама карта**, и это сигнализирует об определённом этапе исполнения команды.
* **Data bit**:
  - Спектрум пишет в `#B3` → бит **аппаратно** ставится в 1;
  - карта читает свой порт `#02` → бит сбрасывается в 0;
  - карта пишет в свой порт `#03` → бит ставится в 1;
  - Спектрум читает `#B3` → бит **аппаратно** сбрасывается в 0.
* «Состояние бита данных очень часто не определено, и если в спецификации команд не определены
  значения этого бита на определённых этапах исполнения команды, недопустимо делать какие-либо
  предположения относительно значения этого бита» (`GSPROG` стр. 208-210) — **это прямой запрет
  гадать по Data bit вне описанных мест**.

**Расхождение по битам 6..1.** Документация говорит «не определены». Обе современные реализации
возвращают единицы: `MISTGS` — `assign DO = A ? {bit7, 6'b111111, bit0} : port_03;` (`gs.v:94`),
`ZXMS` — `wire [7:0] gs_status = {gs_flag_data, 6'b111111, gs_flag_cmd};` (`top.v:231`). На
настоящей карте это, скорее всего, плавающая шина. Значит: **читать эти биты нельзя, но отдавать
их единицами — общепринято**.

## 1.4 Канонические ожидания (то, что крутит весь GS-софт)

`GSPROG` §4, стр. 232-262 задаёт нотацию, которой описаны все команды:

```
GSCOM EQU 187 : GSDAT EQU 179

SC #NN  : LD A,#NN : OUT (GSCOM),A          ; послать команду
SD Data : LD A,Data : OUT (GSDAT),A         ; послать данные

WC : WCLP IN A,(GSCOM) : RRCA : JR C,WCLP   ; ждать СБРОСА Command bit
WD : WDLP IN A,(GSCOM) : RLCA : JR C,WDLP   ; ждать СБРОСА Data bit (карта приняла байт)
WN : WNLP IN A,(GSCOM) : RLCA : JR NC,WNLP  ; ждать УСТАНОВКИ Data bit (байт ОТ карты)
GD Data : IN A,(GSDAT)                      ; забрать байт
<PAUSE> : «просто небольшая задержка кадра два-три»
```

Тайм-аутов в этих циклах нет (проверено по X-Player, Mod Player и драйверу NeoGS —
`НАШЕ`, `GENERAL_SOUND.md:49-52`). Следствие для нас: **работать медленнее настоящей карты законно,
терять байты — нет**.

Отдельно `GSPROG` стр. 266-271 приводит «последовательность против зависания (иногда помогает)»:
`XOR A : OUT (#B3),A : OUT (#BB),A : IN A,(#BB)` — то есть софт имеет право начинать с неё.

## 1.5 Внутренние порты карты (сторона её Z80)

`GSPROG` не описывает их отдельным разделом, но `MISTGS` (`gs.v:23-56`) и `NGSINFO` (стр. 100-118)
совпадают дословно:

| Порт | Направление | Смысл |
|---|---|---|
| `#00` | запись | страничный регистр; **страница 0 = ПЗУ**. `MISTGS`: биты 5..0 (`gs.v:186`, 64 страницы по 32К = 2 МБ). `NGSINFO`: биты 6..0, 7 бит |
| `#01` | чтение | код команды, записанный Спектрумом в `#BB` |
| `#02` | чтение | байт, записанный Спектрумом в `#B3`; **чтение сбрасывает Data bit** |
| `#03` | запись | байт для Спектрума; **запись ставит Data bit** |
| `#04` | чтение | то же слово состояния, что в `#BB` |
| `#05` | чтение или запись | **СБРОС Command bit** — единственный законный способ его снять |
| `#06..#09` | запись | громкости каналов 1..4, биты 5..0, unsigned, 0 = off, 63 = max |
| `#0A` | чтение или запись | Data bit := инверсия бита 0 порта `#00` |
| `#0B` | чтение или запись | Command bit := бит 5 порта `#09` |

Про `#0A`/`#0B` в `NGSPORT` честно написано: «following two ports are useless and very odd… DO NOT
USE THEM!». Тем не менее `MISTGS` (`gs.v:148-149`) и `ZXMS` (`top.v:245, 256`) их реализуют.

**Раскладка памяти карты** (`GSPROG` §2 + `MISTGS` `gs.v:57-66`):

```
#0000-#3FFF  первые 16 КБ ПЗУ
#4000-#7FFF  первые 16 КБ первой страницы ОЗУ
#8000-#FFFF  листаемые страницы по 32 КБ: страница 0 = ПЗУ, 1 = первая страница ОЗУ, 2… = ОЗУ
```

**Как каналы получают сэмплы:** «данные в каналы заносятся при чтении процессором ОЗУ по адресам
`#6000-#7FFF` автоматически» (`MISTGS` `gs.v:65`). Реализация: `cpu_a_bus[15:13] == 3` выбирает
окно, `cpu_a_bus[9:8]` — номер канала, значение конвертируется в знаковое инверсией бита 7
(`gs.v:195-202`). Своих портов у каналов нет — отсюда наш главный прибор «играет или нет»
(`НАШЕ`, `GENERAL_SOUND.md:146-149`).

**Прерывание:** 37.5 кГц (`GSPROG` §1). `MISTGS` делает `ce_37480` (`gs.v:122-138`), `ZXMS` —
делитель на 12 МГц с перезагрузкой по `g_int_cnt[8:6] == 4'b101` (`top.v:160-178`).

## 1.6 Полный список команд

Пометка `(*)` в исходнике означает «недокументированная, гарантии только для v1.04»
(`GSPROG` §4.2, стр. 1208-1210). Формат: аргументы через `SD`, ожидания через `WC`/`WD`/`WN`.

### Ковоксы и прямой вывод в ЦАП
| Код | Имя | Последовательность |
|---|---|---|
| `#00` | Reset flags | `SC #00 : WC` → Data bit=0, Command bit=0 |
| `#01` | Set silence (*) | `SC #01 : WC` — во все ЦАПы `#80` |
| `#02` | Set low volume (*) | `SC #02 : WC` |
| `#03` | Set high volume (*) | `SC #03 : WC` |
| `#04` | Set 'E' 3bits (*) | `SD Chan(#00-#07) : SC #04 : WC` |
| `#05` | Out volume port (*) | `SD Volume(#00-#3F) : SC #05 : WC` |
| `#06` | Send to DAC (*) | `SD Byte : SC #06 : WC` |
| `#07` | Send to DAC + volume (*) | `SD Byte : SC #07 : WC : SD Volume : WD` |
| `#08` | = `#00` | |
| `#09` | Set one's byte volume (*) | `SD ccvvvvvv : SC #09 : WC` (cc — канал) |
| `#0A` | DAC output (*) | `SD Byte : SC #0A : WC : SD Chan(#00-#03) : WD` |
| `#0B` | DAC + volume (*) | `SD Fbyte : SC #0B : WC : SD ccvvvvvv : WD` |

### Доступ к внутренностям карты — **это и есть путь заливки своего драйвера**
| Код | Имя | Последовательность |
|---|---|---|
| `#10` | Out to any port (*) | `SD Port(#00-#09) : SC #10 : WC : SD Data : WD` |
| `#11` | In from any port (*) | `SD Port : SC #11 : WC : GD Data : WN` |
| `#12` | OUT to 0 port (*) | `SD Data : SC #12 : WC` |
| `#13` | **Jump to Address** (*) | `SD ADR.L : SC #13 : WC : SD ADR.H : WD` |
| `#14` | **Load memory block** (*) | `SD LEN.L : SC #14 : <PAUSE>(мб WD) : SD LEN.H : WD : SD ADR.L : WD : SD ADR.H : <PAUSE> :` затем `LEN` пар `SD/WD` |
| `#15` | Get memory block (*) | `SD LEN.L : SC #15 : <PAUSE> : SD LEN.H : WD : SD ADR.L : WD : SD ADR.H : <PAUSE> :` затем `GD/WN` × LEN и финальный `GD` |
| `#16` | Poke to address (*) | `SD Byte : SC #16 : WC : SD ADR.L : WD : SD ADR.H : WD` |
| `#17` | Peek from address (*) | `SD ADR.L : SC #17 : WD : SD ADR.H : GD Byte` |
| `#18` | Load DE Pair (*) | `SD Byte.E : SC #18 : WC : SD Byte.D : WD` |

| `#1A` | Peek from (DE) (*) | `SC #1A : WC : GD Byte : WN` |
| `#1B` | Increment DE (*) | `SC #1B : WC` |
| `#1C` | Poke to (#20XX) (*) | `SD ADR.L : SC #1C : WC : SD Byte : WD` — бессмысленна, там ПЗУ |
| `#1D` | Peek from (#20XX) (*) | `SD ADR.L : SC #1D : WC : GD Byte : WN` |
| `#1E`-`#1F` | зарезервированы | |

**⚠ Внимание на `#14` и `#17`:** в них ожидание записано НЕ как `WC` после команды, а как
`<PAUSE>` («задержка кадра два-три») с пометкой «мб WD». То есть **софт имеет право не ждать флага
вовсе в этом месте**, и это документированное поведение.

| Код | Имя | Последовательность / ответ |
|---|---|---|

| `#21` | Get free RAM | то же (в тексте опечатка — там повторён `SC #20`) |
| `#22` | Get GS Variable (*) | `SD Num : SC #22 : WC : GD Variable : WN` |
| `#23` | **Get number of RAM Pages** | `SC #23 : WC : GD Number_RAM_Pages` — **без ожидания флага после WC**. В базовой версии 3 страницы |
| `#2A` | Set Module Master Volume | `SD Vol[#00..#40] : SC #2A : WC : [GD Old]` |
| `#2B` | Set FX Master Volume | `SD Vol[#00..#40] : SC #2B : WC : [GD Old]` |
| `#2E` | Set Current FX | `SD Cur_FX : SC #2E : WC` — 0 в любой команде «номер сэмпла» подставляет CURFX |
| `#F3` | **Warm restart** | `SC #F3 : WC` — сброс БЕЗ определения и проверки страниц памяти |
| `#F4` | **Cold restart** | `SC #F4 : WC` — полный перезапуск со всеми проверками, «по сути, `JP #0000`» |
| `#F5` | Busy on | `SC #F5 : WC` — флаг занятости := `#FF` |
| `#F6` | Busy off | `SC #F6 : WC` — флаг занятости := `#00` (исходное) |
| `#F7` | Get HX Register (*) | `SC #F7 : WC : GD HX : WN` |
| `#FA` | Out zero_to_zero | `SC #FA : WC` — приостановка звука до следующего чтения любого порта |
| `#F1`,`#F2`,`#F8`,`#F9`,`#FB`-`#FF` | зарезервированы | |

**Главный цикл прошивки** (`GSPROG` §4.1.36, стр. 583-591) — по нему видно, когда карта вообще
смотрит на порты:
```
1 if Command bit = 0 then goto 1
2 Execute Command
3 if Command bit = 1 then goto 2
4 if Playing = 0 then goto 1
5 if Busy = #FF then goto 1
6 Process Sound
7 goto 1
```
Отсюда следствие, на которое мы уже наступали: **в холостом цикле карта регистр данных не читает
вовсе** — значит «держать команду до опустошения очереди данных» приводит к взаимной блокировке.

| `#3E` | Load FX Extended (signed, Amiga) | `SD #01 : SC #3E : WC : [GD FX_Handle]` → далее как `#38` |
| `#39` | Play FX | `SD FX_Handle : SC #39 : WC` |
| `#3A` | Stop FX in channels | `SD Channel_Mask : SC #3A : WC`. **Известный дефект прошивки:** бит 7 маски останавливает НУЛЕВОЙ канал; рекомендация автора — глушить всё маской `#FF` |
| `#3D` | Set FX Volume | `SD Vol : SC #3D : WC : [GD Old]` |
| `#40` | Set FX Note | `SD Note[0..95] : SC #40 : WC`. 36 = C-3, 48 = C-4, 60 = C-5. **В версии 1.04 генераторы Wave 2,3 тянут только октавы 3,4,5 → допустимый диапазон 36..71** |
| `#41` | Set FX Volume | `SD Vol[#00..#40] : SC #41 : WC` |
| `#42` | Set FX Finetune | `SD Finetune : SC #42 : WC` |
| `#45` | Set FX Priority | `SD Prio[#01..#FE] : SC #45 : WC`. По умолчанию `#80`; сэмплы внутри модуля имеют `#40` |
| `#46` | Set Seek First | `SD маска : SC #46 : WC` — младшие 4 бита = каналы 0..3 |
| `#47` | Set Seek Last | как `#46` |
| `#48` | Set Loop Begin (*) | `SD LEN.L : SC #48 : WC : SD LEN.M : WD : SD LEN.H : WD`. `LEN.H = #FF` → зацикливания нет |
| `#49` | Set Loop End (*) | как `#48` |
| `#80`-`#83` | Direct Play FX в канале | `SD Sample : SC #8x : WC` |
| `#88`-`#8B` | + нота | `SD Sample : SC #8x : WC : SD Note : WD` |
| `#90`-`#93` | + громкость | `SD Sample : SC #9x : WC : SD Volume : WD` |
| `#98`-`#9B` | + нота и громкость | `SD Sample : SC #9x : WC : SD Note : WD : SD Volume : WD` |
| `#A0`-`#A3` | Change Channel Note (*) | `SD Note : SC #Ax : WC` — на лету |
| `#A8`-`#AB` | Change Channel Volume (*) | `SD Volume : SC #Ax : WC` — на лету |

**Параметры сэмпла после загрузки** (`GSPROG` §4.1.56, стр. 809-813): `Note=60, Volume=#40,
FineTune=0, SeekFirst=#0F, SeekLast=#0F, Priority=#80, No Loop`, и `CurFX := FX_Handle`.

**Алгоритм выбора канала командой `#39`** (стр. 886-894): сначала свободный канал из `SeekFirst`,
затем свободный из `SeekLast`, затем среди `SeekLast` берётся канал с наименьшим приоритетом, и
если приоритет нового сэмпла выше — старый вытесняется.

**Соответствие каналов Amiga↔GS** (`GSPROG` §4.3): `GS0→AM1, GS1→AM4, GS2→AM2, GS3→AM3`.

### Потоковые команды `#D1`/`#D2`
Отдельного раздела в документе у них нет — они описаны только внутри `#30`/`#38`/`#3E`:
`#D1` = Open Stream, `#D2` = Close Stream (`GSPROG` стр. 709, 718). Диапазон `#B0-#F0` объявлен
зарезервированным (`GSPROG` §4.1.89), то есть `#D1`/`#D2` формально живут внутри «зарезервированного»
диапазона. Другого описания нет ни в одном найденном источнике.

### Команды прошивки v1.05a (bugfix 2007, psb + Evgeny Muchkin)
`GSPROG` §6, стр. 1297-1348:
* исправлены модули с ≥ 63 паттернами, скорость последней ноты, скорость сэмплов, ложная нота в
  `#64` при старте;
* **`#6A` Set player mode:** `SD #01 (On) / #00 (Off) : SC #6A : WC` — карта перестаёт реагировать
  на команду останова `F00` внутри модуля;
* **`#6B` Relooper:** `SD MinLoopLen_Low : SC #6B : WC : SD MinLoopLen_High`; длина **в СЛОВАХ**,
  0..16384, 0 = выключен. Короткая форма (`SC #6B : WC` и сразу следующая команда) даёт 512 слов;
* **настройки `#6A` и `#6B` сбрасываются только аппаратным RESET или командой `#F4`; командой `#F3`
  НЕ сбрасываются**;
* в прошивке по смещению `#0004` лежит номер версии в BCD, по `#0100` — три строки копирайта по
  24 символа, по `#0080` — строка описания патча, оканчивающаяся нулём;
* для старых плееров достаточно из бейсика: `OUT 179,1 : OUT 187,106 : OUT 187,107`.

## 1.7 Что делает карта при сбросе

* **Аппаратный сброс** — карта проходит полную инициализацию: определение количества страниц памяти
  и их проверку (это то, что пропускает `#F3`, см. `GSPROG` §4.1.33). Наша практика: около 5 секунд
  реального времени (`НАШЕ`, `GENERAL_SOUND.md:25-28`).
* `#F4` Cold restart — «по сути, `JP #0000`», то есть полный проход со всеми проверками.
* `#F3` Warm restart — то же, но БЕЗ определения/проверки страниц. Настройки `#6A`/`#6B` переживают.
* Флаг Busy изначально `#00` (`GSPROG` стр. 583).
* `MISTGS` при `RESET` обнуляет `port_BB`, `port_B3`, `port_00`, `port_03` (`gs.v:162-182`);
  `ZXMS` — то же плюс флаги `gs_flag_data`/`gs_flag_cmd` в 0 (`top.v:186-190, 233-234, 249-250`).
* У NeoGS порт конфигурации `#0F` при аппаратном сбросе принимает `00110000` — то есть **Z80 на
  10 МГц** (`NGSINFO` стр. 141). Содержимое страничных портов `#00` и `#10` при сбросе **не
  определено** (`NGSINFO` стр. 102, 144).

## 1.8 Память и страничность

| Что | Оригинальный GS | NeoGS | MiSTer |
|---|---|---|---|
| ОЗУ | 128 КБ (112 КБ доступно) | до 4 МБ | до 4096 КБ (`gs.v:12`) |
| Страничный порт | `#00`, страницы по 32 КБ, страница 0 = ПЗУ (`gs.v:24-26`) | `#00` 7 бит + `#10` (расширенный режим) | `port_00[5:0]` (`gs.v:186`) |
| Расширенный режим | нет | `GSCFG0 (#0F)` бит 3: `#00` → 16К в `#8000-#BFFF`, `#10` → 16К в `#C000-#FFFF` (`NGSINFO` стр. 144-176) | нет |
| Окна WIN0..WIN3 | нет | порты `#20..#23`, страницы по 16 КБ, 0..255 = 0..4 МБ (`NGSPORT:203-206`) | нет |
| Число страниц софту | команда `#23` | она же | она же |

Трансляция обычного режима в расширенный у NeoGS описана точно (`NGSINFO` стр. 158-176):
```
расширенный: порт #00 = axxxxxxx, порт #10 = byyyyyyy
  #8000-#BFFF → малая страница xxxxxxxa
  #C000-#FFFF → малая страница yyyyyyyb
обычный:     порт #00 = zxxxxxxx
  #8000-#BFFF → xxxxxxx0
  #C000-#FFFF → xxxxxxx1
```

**Соответствие объёма и ответа на `#23`** (наш замер, `GENERAL_SOUND.md:204-207`): 128 КБ → 3
страницы (это и есть «базовая версия» из `GSPROG`), 512 КБ → 15. Mod Player v2.5 сверяет ответ
буквально (`CP 3`) и иначе печатает `WARNING! GS, NOT PRESENT?!`; X-Player адресует сэмплы
индексом 3, которого у 128 КБ нет вовсе.

## 1.10 🔴 КАК СОФТ ЗАЛИВАЕТ СВОЙ ДРАЙВЕР В КАРТУ (наше больное место)

Здесь два принципиально разных механизма, и их нельзя путать.

### А. Оригинальный GS: заливка кода в ОЗУ карты штатными командами

Всё делается командами `#14` (Load memory block) и `#13` (Jump to Address), описанными выше. Полная
последовательность:

```
SD LEN.L : SC #14 : <PAUSE>(мб WD) : SD LEN.H : WD : SD ADR.L : WD : SD ADR.H : <PAUSE>
затем LEN раз:  SD байт : WD
затем:  SD ADR.L : SC #13 : WC : SD ADR.H : WD      ; передать управление
```
Мелкая правка — `#16` Poke / `#17` Peek, либо `#18`/`#19`/`#1A`/`#1B` через пару DE карты.
Страницу выбирают заранее через `#12` (OUT to 0 port) или `#10` с портом `#00`.

**Чего софт ждёт в ответ:** только флагов `WC`/`WD` по правилам §1.4 — и **в двух местах не ждёт
ничего, а просто держит паузу в 2-3 кадра** (`#14` и `#15` после кода команды и после `ADR.H`).
Никаких квитанций содержимого нет: прочитать назад можно только `#15` (Get memory block) или `#17`.

### Б. NeoGS: собственный загрузчик прошивки (`NGSLOAD`)

Это то, чего у оригинального GS нет вовсе, и то, на чём мы обязаны споткнуться, если реализуем
только оригинал. Точная последовательность из `NGSLOAD`:

```
LD A,#80 : OUT (GSCTR),A   ; порт #33 — программный сброс NeoGS
NOP : NOP : NOP            ; ждём 12 тактов
LD A,#55 : OUT (GSDAT),A : OUT (GSCOM),A   ; первый ожидаемый байт
CALL WC
LD A,#AA : OUT (GSDAT),A : OUT (GSCOM),A   ; второй ожидаемый байт
CALL WC                    ; здесь ждать ДОЛЬШЕ: идёт перенос кода загрузчика из ПЗУ в ОЗУ
```
Логика самого загрузчика (`NGSLOAD`, «Последовательность работы»):
1. после программного сброса со стороны Спектрума — **задержка с ожиданием определённых байт**
   через порты команд и данных;
2. **при превышении лимита ожидания** — попытка загрузить прошивку `NEOGS.ROM` из корня встроенной
   SD-карты (только короткие имена);
3. если файла нет — загружается и запускается прошивка из ПЗУ.

Команды загрузчика подаются тем же способом (`SD` параметр, потом `SC` код), `WC`/`WD`/`WN` те же:

| Код | Что |
|---|---|
| `#00` | загрузить со Спектрума 32 КБ прошивки в страницу 0, адрес 0 (не запускать). Поток: `OUTI : CALL WD` × `#8000` |
| `#01` | запустить прошивку; ставит защиту от записи страницы 0 и частоту 20 МГц |
| `#02` | загрузить и запустить прошивку из ПЗУ (полностью старое поведение) |
| `#03` | загрузить и запустить прошивку с SD |
| `#04` | загрузка кода со Спектрума в любую страницу по адресу `#8000`, до 32 КБ. Сначала `SD страница : SC 4 : WC`, затем длина `E`,`D` через `OUT (C)`+`WD`, затем поток |
| `#05` | загрузка файла с SD по пути `DIR1/DIR2/FILE.EXT`, ВЕРХНИМ регистром, строка оканчивается нулём; в страницы `#02..#7F`; страница 1 запрещена |
| `#06` | запуск кода: `SD страница : SC 6 : WC : SD ADR.L : WD : SD ADR.H : WD` |
| `#07` | статус последнего загруженного файла: `#00` загружен, `#AA` не найден, `#DD` FAT не обнаружен, `#EE` SD не инициализирована/отсутствует |
| `#08` | текстовая строка версии страницы (поток `WN` + `IN`, до нулевого байта) |
| `#09` | CRC16 заголовка/блока (не для применения) |
| `#0A` | загрузить файл обновления `NGS_ROM.UPD` из корня SD |
| `#0B` | частота процессора: 0 = 10, 1 = 12, 2 = 20, 3 = 24 МГц; бит 7 в параметре = прочитать текущую |

**Что из этого следует для нас.** Софт, который умеет NeoGS (плееры NGS, Z-Player поздних версий),
начинает с записи `#80` в порт `#33`. Если порта `#33` нет, запись улетает в никуда (или, хуже, в
чужой декодер), карта не сбрасывается, `#55`/`#AA` уходят в обычный командный интерпретатор gs105
как **неизвестные команды**, и дальше поведение непредсказуемо. Штатный выход из этой ситуации у
самого загрузчика — тайм-аут, но тайм-аут отсчитывает **загрузчик NeoGS**, которого у нас нет.

## 2.1 Карта портов NEMO

Схема: `nedopc.com/NEMOIDE/nemohddsch.png` (ссылка из `НАШЕ`, `sources/nemo_ide.v:9`).
Порты (`НАШЕ` `nemo_ide.v:12-16`, независимо подтверждено `EVOPORT` `zports.v:257-272`):

| Порт | Что | Порт | Что |
|---|---|---|---|
| `#10` | CS0 reg0 — Data, младшие D0-D7 | `#90` | CS0 reg4 — LBA1 / Cylinder Low |
| `#11` | защёлка старшего байта D8-D15 | `#B0` | CS0 reg5 — LBA2 / Cylinder High |
| `#30` | CS0 reg1 — Error (чтение) / Features (запись) | `#D0` | CS0 reg6 — Drive/Head, LBA3 |
| `#50` | CS0 reg2 — Sector Count | `#F0` | CS0 reg7 — Status (чтение) / Command (запись) |

`EVOPORT` перечисляет также остальные семь портов группы CS1: `#08, #28, #48, #68, #88, #A8, #C8,
#E8` (`zports.v:266-273`) и отдаёт по ним тот же `iderdeven` (`zports.v:405-408`).

### Дешифрация — здесь три источника, и они НЕ совпадают

* **`EVOPORT`** (`zports.v:337-341`):
  ```
  ide_all  = ide_even || ide_port11;
  ide_even = (loa[2:0] == 3'b000) && (loa[3] != loa[4]);   // чётные порты
  ide_port11 = (loa == 8'h11);
  ```
  То есть: **A2..A0 = 000** и **A3 ≠ A4** (ровно один из двух chip select активен), плюс ровно
  один порт `#11` для старшей защёлки.
* **`UNREAL`** (`io.cpp:490-506` запись, `io.cpp:1268-1279` чтение):
  ```
  if (!(port & 6) && (ide_scheme == IDE_NEMO || IDE_NEMO_A8)) {
      hi_byte = (scheme == IDE_NEMO) ? (port & 1) : (port & 0x100);
      if (hi_byte) → регистр защёлки старшего байта;
      if ((port & 0x18) == 0x08) → CS1: отвечаем ТОЛЬКО если (port & 0xE0) == 0xC0, иначе 0xFF;
      if ((port & 0x18) != 0x10) → return 0xFF;  // недопустимая комбинация CS0/CS1
      → CS0, номер регистра из port>>5
  }
  ```
  То есть A1, A2 = 0 (A0 отдан под защёлку), CS0 требует `A4=1, A3=0`, CS1 требует `A3=1, A4=0`,
  **и в группе CS1 отвечает только регистр 6 (`#C8`)**.
* **`НАШЕ`** (`nemo_ide.v:80-87`): `ebl = A1=0 & A2=0`, `cs0 = ebl & ~A3`, `cs1 = ebl & ~A4 & A3`,
  `hi = A0`, `rg = A[7:5]`. Комбинация `A3=0, A4=0` у нас даёт CS0, у обоих эталонов — «не наш порт».

**Вариант IDE_NEMO_A8** (`UNREAL` `emul.h:52`, `config.cpp:711`): старший байт данных выбирается не
A0, а **A8** (`port & 0x100`), то есть `#11` заменяется на `#0110`. Есть ещё `NEMO-DIVIDE` —
DivIDE-совместимые регистры на NEMO-портах (`io.cpp:128-129, 1077-1078`).

### Две мины схемы (обе из разбора, `НАШЕ` `nemo_ide.v:22-31`)

1. **Все командные порты NEMO чётные**, то есть это порты ULA `#FE`. На Пентагоне `#FE`
   декодируется только по A0=0 → `IN A,(#F0)` без мер вернёт клавиатуру, а `OUT (#10)` будет мигать
   бордюром на каждом байте сектора. В железе решается сигналом **/IORQCE**: плата давит дешифратор
   портов материнки на всё окно EBL. `EVOPORT` делает то же через `porthit` (`zports.v:330-334`) —
   IDE входит в список «наших» портов и внешний декодер их не видит.
2. **Kempston-джойстик.** Если он декодируется по «A5 = 0», то перехватит `#10/#30/#50/#70`.
   В UnrealSpeccy блок NEMO стоит СТРОГО РАНЬШЕ kempston (`io.cpp:1268` против `io.cpp:1283`).

**M1 в гейте обязателен**, иначе цикл подтверждения прерывания попадёт в трап.

### Порядок 16-битного обмена (две внешние защёлки, отдельные на чтение и запись)

* **чтение**: сначала `#10` (даёт младший байт и **попутно защёлкивает старший**), потом `#11`;
* **запись**: сначала `#11` (в защёлку), потом `#10` (выставляет сразу 16 бит и даёт строб).

(`НАШЕ` `nemo_ide.v:33-36`; та же модель у `UNREAL`: `comp.ide_write`/`comp.ide_read` — отдельные
защёлки на запись и чтение, `io.cpp:494, 1270`.)

| 5 | Cylinder High / LBA[23:16] | — |
| 6 | Device/Head | Alternate Status (R) / Device Control (W) |
| 7 | Status (R) / Command (W) | Drive Address (R) |

### Регистр состояния (Status, `#F0` на чтение; Alt Status `#C8`)

| Бит | Имя | Смысл |
|---|---|---|
| 7 | **BSY** | устройство занято; **при BSY остальные биты недействительны**, файл регистров хосту трогать нельзя |
| 6 | **DRDY** | устройство готово принимать команды |
| 5 | DF / DWF | ошибка устройства (device fault) |
| 4 | DSC | device seek complete |
| 3 | **DRQ** | в буфере лежат данные — забирай (чтение) или клади (запись) |
| 2 | CORR | данные исправлены (устарело) |
| 1 | IDX | **объявлен устаревшим начиная с ATA-4**; настоящие диски его не выставляют |
| 0 | **ERR** | команда завершилась ошибкой; подробности — в регистре Error |

`LSIDE` использует только четыре: `ERR = 0x01, DRQ = 0x08, DRDY = 0x40, BSY = 0x80`
(`ide.c:55-58`). Значение «готов, ошибок нет» = `0x50` (DRDY|DSC), «готов, данные есть» = `0x58`.
После сброса `LSIDE` ставит `0x40` живому устройству и `0xFF` отсутствующему (`ide.c:377-400`) —
то есть «диска нет» показывается как **все единицы**, а не ноль.

### Регистр ошибки (Error, `#30` на чтение)

`LSIDE` `ide.c:72-75`: `OK = 0x00, ABRT = 0x04, IDNF = 0x10, UNC = 0x40`. Полный набор ATA:
бит 0 AMNF, бит 1 TK0NF/T0NF, бит 2 **ABRT** (команда прервана), бит 4 **IDNF** (сектор не найден),
бит 6 **UNC** (некорректируемая ошибка данных), бит 7 BBK (сбойный блок).

**⚠ Одно место, где регистр читается иначе:** после команды `0x90 EXECUTE DEVICE DIAGNOSTIC` при
**снятом** ERR регистр `#30` содержит **код диагностики** (`0x01` = устройство 0 исправно), а не
код ошибки. При поднятом ERR это обычный регистр ошибки, где `0x01` = сбойный блок носителя
(`НАШЕ`, `loader_main.c:7042-7050` — разбор, из-за которого мы чуть не сообщили драйверу «диск
сыпется» вместо «команда не вышла»).

### Регистр Device/Head (`#D0`)

| Бит | Смысл |
|---|---|
| 7 | всегда 1 (obsolete) |
| **6** | **LBA**: 1 = линейная адресация, 0 = CHS |
| 5 | всегда 1 (obsolete) |
| **4** | **DEV**: 0 = master, 1 = slave |
| 3..0 | номер головки (CHS) **или** LBA[27:24] |

`LSIDE` `ide.c:62-68`: `LIBSPECTRUM_IDE_HEAD_LBA = 0x40`. Значение по сбросу у нас — `0xE0`
(`nemo_ide.v:273`), то есть master, LBA. `UNREAL` различает устройства через
`(reg.devhead ^ device_id) & 0x10` (`hdd.cpp:220, 228, 471`).

### Регистр Device Control (`#C8` на запись)

| Бит | Смысл |
|---|---|
| 2 | **SRST** — программный сброс интерфейса |
| 1 | **nIEN** — 1 запрещает прерывание INTRQ |
| 0 | всегда 0 |

`UNREAL` использует `CONTROL_nIEN` (`hdd.cpp:220`) — при поднятом nIEN и при выборе не своего
устройства чтение отдаёт `0xFF`.

## 2.3 Адресация: CHS против LBA

Эталон — `LSIDE` `ide.c:645-726`, функция `seek()`:

```c
if( chn->head & LIBSPECTRUM_IDE_HEAD_LBA ) {          /* бит 6 регистра #D0 */
    sectornumber = ((head & 0x0F) << 24) + (cylinder_high << 16)
                 + (cylinder_low << 8) + sector;
} else {
    cylinder = (cylinder_high << 8) | cylinder_low;
    head     = head & 0x0F;
    sector   = sector - 1;                            /* сектор CHS 1-based! */
    if (cylinder >= drv->cylinders || head >= drv->heads ||
        sector < 0 || sector >= drv->sectors) sectornumber = -1;
    else sectornumber = ((cylinder * drv->heads + head) * drv->sectors) + sector;
}
if (sectornumber < 0 || sectornumber >= cylinders*heads*sectors) {
    status |= ERR;  error = ABRT | IDNF;  return ошибка;
}
```

Три обязательных вывода:
1. **Режим выбирает бит 6 регистра `#D0`, и его надо проверять.** Одни и те же байты в `#70/#90/#B0`
   означают разное.
2. **В CHS номер сектора считается с единицы**, в LBA — с нуля.
3. **Геометрия (cylinders/heads/sectors) обязана быть известна устройству** — иначе CHS не
   пересчитать вовсе. `LSIDE` берёт её из IDENTIFY-блока в заголовке HDF (`ide.c:241-247`).

### Продвижение регистров при многосекторной передаче

По ATA устройство обязано **декрементировать Sector Count** и **вести адрес** по мере передачи.
`LSIDE` `ide.c:686-723` делает это явно: в LBA-режиме инкрементирует `sector → cylinder_low →
cylinder_high → head[3:0]` с переносами; в CHS — `sector = (sector % spt) + 1`, при переходе на 1
инкремент головки по модулю `heads`, при обороте головки — инкремент цилиндра.

## 2.4 Порядок команд

### READ SECTOR(S) — `0x20` (с повторами) / `0x21` (без повторов)

Хост:
1. дожидается `BSY=0, DRQ=0`;
2. пишет `#50` Sector Count (**0 означает 256 секторов**), `#70/#90/#B0` адрес, `#D0` устройство и
   режим;
3. пишет код команды в `#F0`. **Устройство обязано поднять BSY в том же цикле** (иначе драйвер,
   честно дождавшийся снятия BSY, прочитает состояние ПРОШЛОЙ команды — `НАШЕ` `nemo_ide.v:131-138`);
4. дожидается `BSY=0 && DRQ=1`, читает 256 слов через `#10`/`#11`;
5. на промежуточном блоке устройство снова поднимает BSY, готовит следующий сектор и снова даёт DRQ;
6. после последнего блока DRQ снят, статус `0x50`.

`LSIDE` `ide.c:781-803`: `seek()`, затем `read_hdf()`, затем «Initiate the PIO input phase»
(`phase = PIO_IN; status |= DRQ; datacounter = 0`), а при ошибке чтения — `status |= ERR;
error = ABRT | UNC`.

### WRITE SECTOR(S) — `0x30` / `0x31`
`LSIDE` `ide.c:805-817`: `seek()`, затем `phase = PIO_OUT; status |= DRQ`. Хост пишет 256 слов, по
последнему устройство поднимает BSY и сбрасывает данные на носитель.

### EXECUTE DEVICE DIAGNOSTIC — `0x90`
Ответ — **не только код в `#30`, но и СИГНАТУРА в файле регистров**: `#50 = 0x01, #70 = 0x01,
#90 = 0x00, #B0 = 0x00` (для ATA-устройства; у ATAPI сигнатура `#90 = 0x14, #B0 = 0xEB`). Драйверы
NEMO (проверено на Proteus File Manager) без сигнатуры считают, что диска нет (`НАШЕ`
`loader_main.c:7030-7049`). Код `0x01` в `#30` = «устройство 0 исправно».

### INITIALIZE DEVICE PARAMETERS — `0x91`
Хост задаёт трансляцию **до** команды: `#50` = секторов на дорожку, младший полубайт `#D0` = число
головок минус 1. `LSIDE` реализует её (`ide.c:41, 819+`).

### IDENTIFY DEVICE — `0xEC`
Устройство отдаёт **один блок из 256 слов** через тот же PIO-механизм: BSY, затем DRQ, затем
512 байт, затем DRQ снят.

## 2.5 Что обязано быть в ответе IDENTIFY

Слова (16-битные, little-endian), которые реально проверяет ZX-софт:

| Слово | Что |
|---|---|
| 0 | General configuration. Бит 15 = 0 у ATA-устройства; `0x0040` = «несъёмный носитель, фиксированный диск» |
| 1 | число цилиндров |
| 3 | число головок |
| 6 | секторов на дорожку |
| 10..19 | **серийный номер, 20 символов ASCII** |
| 23..26 | версия микрокода, 8 символов |
| 27..46 | **модель, 40 символов ASCII** |
| 47 | максимум секторов в одной команде READ/WRITE MULTIPLE |
| 49 | Capabilities; **бит 9 = поддержка LBA** |
| 53 | Field validity; бит 0 = «слова 54..58 достоверны» |
| 54..56 | текущие логические цилиндры/головки/секторы |
| 57..58 | текущая ёмкость в секторах (32 бита) |
| 60..61 | **общее число адресуемых секторов LBA (32 бита)** |

`LSIDE` `ide.c:728-779` заполняет ровно этот набор: копирует `hdf.drive_identity` (`0x6A` = 106
байт), затем **дописывает** слово 53 = `0x01`, слова 54/55/56 = cylinders/heads/sectors, 57/58 =
ёмкость, и **слова 60/61 — только если в слове 49 стоит бит `0x0200`** (LBA поддерживается).

**Строки в ATA лежат ПОБАЙТНО ПЕРЕВЁРНУТЫМИ внутри 16-битных слов** (первый символ — в старшем
байте). Это свойство спецификации, а не ошибка. Диагностический признак у нас: `zxfdisk` напечатал
`BBLLUTARDI EDI AMEG` вместо `BULBULATOR IDE IMAGE`, и тем самым доказал, что блок доходит
байт-в-байт (`НАШЕ` `loader_main.c:6734, 6743-6752`).

**Как софт определяет ёмкость.** Порядок предпочтения: если слово 49 бит 9 = 1 → слова 60/61 (LBA);
иначе `cylinders × heads × sectors` из слов 1/3/6 либо 54/55/56. Именно так считает `LSIDE`
(`ide.c:733`: `sector_count = drv->cylinders * drv->heads * drv->sectors`).

# 3. РАЗМЕТКА НОСИТЕЛЕЙ

## 3.1 Таблица разделов (MBR)

`MBRSPEC`. Первый сектор диска, 512 байт:

| Смещение | Размер | Что |
|---|---|---|
| `0x000` | 446 | код начального загрузчика |
| `0x1BE` | 64 | таблица разделов: 4 записи по 16 байт |
| `0x1FE` | 2 | подпись `55 AA` |

Запись раздела (16 байт):

| Смещение | Размер | Поле | Обязательно? |
|---|---|---|---|
| +0x00 | 1 | признак активности: `0x80` активный, `0x00` нет | нет |
| +0x01 | 3 | CHS начала (головка, сектор+старшие биты цилиндра, цилиндр) | нет, если софт работает по LBA |
| +0x04 | 1 | **тип раздела** | **да** |
| +0x05 | 3 | CHS конца | нет |
| +0x08 | 4 | **LBA начала (32 бита, little-endian)** | **да** |
| +0x0C | 4 | **размер в секторах (32 бита)** | **да** |

Типы, которые встречаются на ZX-носителях:

| Код | Что | Примечание |
|---|---|---|
| `0x01` | FAT12 | |
| `0x04` | FAT16 < 32 МБ, CHS | |
| `0x06` | FAT16B, CHS | самый частый на «жизненных» ZX-образах |
| `0x0B` | FAT32, CHS | |
| `0x0C` | FAT32, LBA | |
| `0x0E` | FAT16B, LBA | |
| `0x05`/`0x0F` | расширенный раздел | **esxDOS их не поддерживает** |

`MBRSPEC`: «Microsoft implementations enforce CHS access for FAT16B and FAT32 partition types
0x06/0x0B, whereas LBA is used for 0x0E/0x0C».

**Открытый вопрос, который мы уже щупали.** Proteus не показывает раздел типа `0x06` (чужой образ
`0:/HDD16.HDF`), тогда как FATALL тот же образ читает. У нас в прошивке ради этого есть
экспериментальная подмена типа `0x04`/`0x06` на `0x0E` в отдаваемом машине MBR
(`НАШЕ` `loader_main.c:6535-6539, 6853-6859`, включается `gs_ctl = 8`). Вывод не сделан: это
«Proteus не умеет FAT16» или «Proteus не берёт разделы без признака LBA» — см. раздел «Чего мы не
знаем».

## 3.2 Что принимает ZX-софт

**esxDOS** (`ESXDOC`, `esxdos080/docs/readme.txt:4-9`) — прямая цитата:
> Full FAT16/FAT32 read/write support (**no 64K clusters, no extended partitions, no LFN**).

Плюс (`readme.txt:118-122`):
> Drives are named according to their type and partition number. So for the first hard drive and
> partition, it would be named hd0.
>
> Altough ESXDOS itself supports long filenames, the current FAT driver does not. So, for now,
> filenames are limited to the original 8.3 format.

И структура системного диска (`readme.txt:29-36`): в корне обязаны быть `/SYS` (`esxdos.sys`,
`nmi.sys`, `.ko`-модули) и `/BIN`; `/TMP` создать самому. В 0.8.5+ то же, но для DivIDE `/TMP`
явно назван обязательным (`esxdos089/README.TXT:16`).

## 3.3 FAT12/16/32 — что критично

`FATGEN`:

* **Определение типа делается ТОЛЬКО по числу кластеров:**
  `if (CountofClusters < 4085) FAT12; else if (CountofClusters < 65525) FAT16; else FAT32;`
  Ни подпись `FAT16   ` в загрузочном секторе, ни тип раздела в MBR не являются определяющими.
* **`BPB_SecPerClus`** — степень двойки из `1, 2, 4, 8, 16, 32, 64, 128`; «a value should never be
  used that results in a "bytes per cluster" value greater than 32K». Про 64 КБ прямо: такие
  кластеры «do not work properly; do not try to define one» — и это ровно то, что запрещает
  esxDOS.
* **`BPB_NumFATs`** — «This field should always contain the value 2 for any FAT volume of any type».
* **`BPB_RootEntCnt`** — у FAT32 обязан быть 0; у FAT16 рекомендовано 512.
* **`BPB_RsvdSecCnt`** — не 0; у FAT12/16 «should never be anything other than 1», у FAT32 обычно 32.
* **Длинные имена (LFN)** — расширение VFAT: каскад записей каталога с атрибутом `0x0F`. esxDOS их
  не читает, а наличие LFN-записей «съедает» ёмкость каталога: имя вроде
  `Manic Miner (1983)(Bug-Byte).tap` занимает четыре записи вместо одной
  (`НАШЕ` `arm/divmmc_fs.h:27-31`).

## 3.4 Формат RS-IDE (.hdf)

`HDFSPEC` + эталонная реализация `LSIDE` (`ide.c:212-247`).

**Версия 1.0** (revision `0x10`):

| Смещение | Размер | Что |
|---|---|---|
| `0x00` | 6 | подпись `RS-IDE` |
| `0x06` | 1 | `0x1A` |
| `0x07` | 1 | версия в BCD: `0x10` |
| `0x08` | 1 | флаги; **бит 0 = halved sector data** (в файле хранится только младший байт каждого слова) |
| `0x09` | 2 | **смещение данных**, little-endian, `0x0080` |
| `0x0B` | 11 | резерв, нули |
| `0x16` | 106 | блок ответа IDENTIFY DEVICE |
| `0x82`+ | — | сырые данные диска |

**Версия 1.1** (revision `0x11`): всё то же, но блок IDENTIFY занимает **512** байт, смещение
данных `0x0216`. Разница только в том, что в 1.1 помещается полная информация о числе секторов LBA.

Проверка подписи у `LSIDE` (`ide.c:224-231`): `memcmp(signature,"RS-IDE",6)` **и** `id == 0x1a`.
Разбор (`ide.c:236-247`):
```c
data_offset = (datastart_hi << 8) | datastart_low;      /* поле по 0x09 */
sector_size = (flags & 0x01) ? 256 : 512;
cylinders = GET_WORD(drive_identity, NUM_CYLINDERS);     /* слово 1  */
heads     = GET_WORD(drive_identity, NUM_HEADS);         /* слово 3  */
sectors   = GET_WORD(drive_identity, NUM_SECTORS);       /* слово 6  */
```

### 🔴 Восьмибитный режим — точное правило

`LSIDE` `ide.c:409-460` (чтение) и `472-499` (запись):
```c
/* чтение: из файла берётся sector_size (= 256) байт */
if (drv->sector_size == 256) {
    for (i = 0; i < 256; i++) {
        dest[i*2]     = buffer[i];      /* младший байт слова — из файла */
        dest[i*2 + 1] = 0xff;           /* СТАРШИЙ БАЙТ = 0xFF          */
    }
} else memcpy(dest, buffer, 512);

/* запись: обратно кладётся только каждый ЧЁТНЫЙ байт */
if (drv->sector_size == 256) { for (i = 0; i < 256; i++) buffer[i] = src[i*2]; }
```
То есть: сектор в файле занимает **256 байт**, разворачивается в 512 байт логического сектора
подстановкой `0xFF` в старшие байты, и смещение сектора считается как
`data_offset + 256 × номер_сектора`.

Живой пример восьмибитного образа для сверки: `/tmp/hdimg/software8.hdf` — `ver=10, flags=01,
dataoff=0x80`, парный ему шестнадцатибитный `/tmp/hdimg/software16.hdf` — `ver=10, flags=00`.

## 3.5 Чем НАША разметка отличается от типовой «жизненной»

Замер образов на ThinkPad (`/tmp/anahdf2.py`, 09.08.2026):

| Образ | Версия | Тип раздела | Начало | ФС | Кластер | Копий FAT | Корень | OEM |
|---|---|---|---|---|---|---|---|---|
| `divide.hdf` (эталон из сети) | 1.1 | `0x06` FAT16 CHS | LBA 63 | FAT16 | 4 сект = 2 КБ | 2 | 512 записей | нули |
| `hdd.hdf` (наш рабочий) | 1.1 | `0x06` | LBA 63 | FAT16 | 2 КБ | 2 | 512 | нули |
| `oleg.hdf` (чужой) | 1.1 | `0x06` | LBA 63 | FAT16 | 2 КБ | 2 | 512 | нули |
| `hdd32.hdf` (наш) | 1.1 | `0x0C` FAT32 LBA | LBA 63 | FAT32 | **1 сектор = 512 байт** | 2 | 0 | `mkfs.fat` |
| `hdd32b.hdf`, `hddgs.hdf` (наши) | 1.1 | `0x0C` | LBA 63 | FAT32 | 8 сект = 4 КБ | 2 | 0 | `MSWIN4.1` |

Отличия и чем они грозят:

1. **`hdd32.hdf` сделан `mkfs.fat` с кластером 512 байт** на 64-мегабайтном разделе. Формально
   законно (`FATGEN` разрешает `SecPerClus = 1`), но это ~130 тысяч кластеров и таблица размещения
   в 1008 секторов на копию. Ни один «жизненный» образ так не выглядит: Windows на таком объёме
   даёт 4 КБ. Риск — не в стандарте, а в чужом коде: 16-битные счётчики кластеров и медленный
   обход таблицы на Z80.
2. **FAT32 на 64 МБ вообще нетипичен.** Порог `FATGEN` пройден (65525 кластеров есть), но
   исторический ZX-софт видел FAT32 только на больших дисках; FAT16 — на всём.
3. **Поле OEM пустое** у `hdd.hdf`/`divide.hdf` (восемь нулей). `FATGEN` это поле не считает
   значимым, но существуют драйверы, которые по нему опознают форматтер.
4. **Начало раздела LBA 63** — CHS-выравнивание на границу дорожки при 63 секторах на дорожку.
   Это согласуется с нашей синтезированной геометрией 16 головок × 63 сектора, и это правильно.
5. **Признак LBA у типа раздела.** Наши FAT32-образы имеют `0x0C` (LBA), FAT16 — `0x06` (CHS).
   Для софта, который переключается на CHS по типу раздела, это разные дороги — см. открытый
   вопрос с Proteus.
6. **Все наши образы — версии 1.1** (`data_offset = 0x216`), то есть с полем IDENTIFY на 512 байт.
   Мы его при этом не используем (см. «Где мы отступаем»).

# 4. DivMMC И esxDOS

## 4.1 Что общего у DivIDE и DivMMC

С точки зрения программ они одинаковы: та же подмена страницы ПЗУ по особым адресам, то же
собственное ОЗУ, та же esxDOS. Отличается только транспорт носителя — параллельный ATA против карты
памяти по последовательной шине (`НАШЕ`, `/tmp/divmmc_req.md`, требования владельца 09.08).

## 4.2 Ловушки адресов (автомаппер)

`VELESOFT` — устройство «маппится автоматически, когда процессор выбирает опкод по адресам»:
`0000h, 0008h, 0038h, 0066h, 04C6h и 0562h`, плюс мгновенное включение при выборке из области
`3D00h-3DFFh` («100 ns после /MREQ»). Выключение — в цикле регенерации при выборке из области
`1FF8h-1FFFh`.

`MISTDIV` реализует это дословно (`divmmc.v:109-122`):
```verilog
if (m1 & ~old_m1) begin
    casex(addr)
        16'h0000, 16'h0008, 16'h0038, 16'h0066:
            m1_trigger <= 1;                   // включить автомаппер ПОСЛЕ этого цикла
        16'h04C6, 16'h0562:
            m1_trigger <= !disable_pagein;     // отключаемо, если играет встроенный магнитофон
        16'h3DXX:
            {automap, m1_trigger} <= 2'b11;    // включить НЕМЕДЛЕННО
        16'b0001111111111XXX:                  // 1FF8...1FFF
            m1_trigger <= 0;                   // выключить ПОСЛЕ этого цикла
    endcase
end
if (~nRFSH) automap <= m1_trigger;
```
Два разных момента включения (немедленно для `3Dxx`, «после цикла» для остальных) — это не
украшение: `3Dxx` — вход в TR-DOS, и страница обязана появиться до чтения следующего байта.

## 4.3 Порты

| Порт | DivIDE | DivMMC | ZXMMC |
|---|---|---|---|
| `#E3` | **CONTROL** (`VELESOFT`; `FUSEDIV` `divide.c:55`: маска `0x00FF`, значение `0x00E3`) | **CONTROL** (`FUSEDIV` `divmmc.c:56`; `MISTDIV` `divmmc.v:104`) | — |
| `#E7` | — | **CS** (выбор карты; `MISTDIV` `divmmc.v:56`, `FUSEDIV` `divmmc.c:57`) | — |
| `#EB` | — | **DATA** (SPI обмен; `MISTDIV` `divmmc.v:58`, `FUSEDIV` `divmmc.c:58`) | — |
| `#1F` | — | — | CS (`MISTDIV` `divmmc.v:57`) |
| `#3F` | — | — | DATA (`MISTDIV` `divmmc.v:59`) |
| `#A3,#A7,#AB,#AF,#B3,#B7,#BB,#BF` | **регистры ATA 0..7** (`FUSEDIV` `divide.c:53-54, 191-208`: маска `0x00E3`, значение `0x00A3`) | — | — |

**🔴 Конфликт, о котором надо помнить:** регистры ATA DivIDE `#B3` и `#BB` — это ровно порты
General Sound. Отсюда же реплика в документации NeoGS про «системный порт со стороны ZX — `#B3` при
активном DOS» (`NGSINFO:7`). Наш выбор DivMMC (`#E3/#E7/#EB`) конфликта не имеет.

## 4.4 Регистр управления `#E3` и страничность

Биты (`VELESOFT`, подтверждено `MISTDIV` `divmmc.v:104`: `{conmem, mapram, sram_page} <= {din[7:6], din[3:0]}`):

| Бит | Имя | Что |
|---|---|---|
| 7 | **CONMEM** | безусловно включить память интерфейса |
| 6 | **MAPRAM** | режим «ОЗУ вместо ПЗУ» |
| 3..0 | **BANK** | номер страницы ОЗУ 8 КБ в окне `2000-3FFF` |

Раскладка (`VELESOFT` + `MISTDIV` `divmmc.v:85-90`):

| Режим | `0000-1FFF` | `2000-3FFF` |
|---|---|---|
| CONMEM = 1 | ПЗУ интерфейса (пишется, если джампер открыт) | выбранная страница 0..3, всегда пишется |
| MAPRAM = 1, CONMEM = 0 | **банк 3, только чтение** | выбранная страница (кроме банка 3) |
| всё в нулях, автомаппер снят | обычная память Спектрума | обычная память Спектрума |

`MISTDIV` формулирует то же выражениями:
```verilog
rom_active = nRFSH & page0 & (conmem | (!mapram & automap));
ram_active = (nRFSH & page0 & !conmem & mapram & automap) | (page1 & (conmem | automap));
ram_bank   = page0 ? 4'h3 : sram_page;
```
**Сброс:** «All bits are reset to '0' after each power-on» (`VELESOFT`). `MISTDIV` при выключенном
режиме гасит всё: `m1_trigger, automap, conmem, sram_page, mapram <= 0` (`divmmc.v:124-130`).

Режимы модуля (`MISTDIV` `divmmc.v:10`): `00` выкл, `01` divmmc, `10` zxmmc, `11` divmmc+esxdos.
**Автомаппер работает только в режиме `11`** (`divmmc.v:100`) — то есть подмена страниц по адресам
включается ровно тогда, когда в ПЗУ лежит esxDOS.

## 4.5 Последовательный обмен

`MISTDIV` (`divmmc.v:64-82`):
* запись в `#E7` (`port_cs`): `spi_ss <= din[0]` — бит 0 гонит /CS карты;
* запись в `#EB` (`port_io`): строб передачи `tx_strobe`;
* чтение `#EB`: строб приёма `rx_strobe` (передаётся `0xFF`).

Сам сдвигатель (`divmmc.v:152-190`): 8 бит, `counter[4]` = готовность, `spi_clk = counter[0]`,
данные сдвигаются вверх (`spi_do = io_byte[7]`), приём по фронту `spi_clk`. На чтении в карту
уходит `0xFF` (`io_byte <= tx ? din : 8'hff`) — это стандартное «холостое» слово SPI.

## 4.6 Набор команд карты в последовательном режиме

`ELMMMC`. Кадр команды: 2 стартовых бита `01`, 6 бит индекса, 32 бита аргумента, 7 бит CRC,
стоповый бит — всего 6 байт.

Ответ **R1** (1 байт): бит 0 In Idle State, 1 Erase Reset, 2 Illegal Command, 3 CRC Error,
4 Erase Sequence Error, 5 Address Error, 6 Parameter Error, 7 всегда 0.
**R3** = R1 + 32 бита OCR. **R7** = R1 + 32 бита ответа CMD8.

Инициализация:

| Шаг | Команда | Аргумент | Ответ | Что |
|---|---|---|---|---|
| 1 | **CMD0** GO_IDLE_STATE | 0 | R1 | перевод в SPI-режим (при поднятом /CS и ≥74 холостых тактах) |
| 2 | **CMD8** SEND_IF_COND | `0x000001AA` | R7 | опознание SDC v2 |
| 3 | **CMD55** + **ACMD41** | HCS в аргументе | R1 | инициализация SDC, повторять до снятия бита idle |
| 3' | **CMD1** SEND_OP_COND | 0 | R1 | то же для MMC |
| 4 | **CMD58** READ_OCR | 0 | R3 | признак SDHC/SDXC (блочная адресация) |
| 5 | **CMD16** SET_BLOCKLEN | 512 | R1 | длина блока |

Обмен данными:

| Команда | Индекс | Что |
|---|---|---|
| READ_SINGLE_BLOCK | **CMD17** | один блок |
| READ_MULTIPLE_BLOCK | **CMD18** | подряд |
| WRITE_BLOCK | **CMD24** | один блок |
| WRITE_MULTIPLE_BLOCK | **CMD25** | подряд |
| STOP_TRANSMISSION | **CMD12** | конец многоблочной передачи |
| SEND_CSD / SEND_CID | **CMD9 / CMD10** | параметры карты, в том числе ёмкость |

Токены: старт блока при чтении и одиночной записи `0xFE`, старт блока при многоблочной записи
`0xFC`, конец многоблочной записи `0xFD`. Ответ на записанный блок — байт, у которого биты 2..0:
`101` принято, `010` ошибка CRC, `110` ошибка записи.

## 4.7 Чего esxDOS требует от носителя

Сведено из `ESXDOC`:
* MBR с разделом FAT16 или FAT32 (**расширенные разделы не читаются**);
* кластер **не 64 КБ**;
* имена **8.3**, LFN не читаются;
* в корне системного диска — `/SYS` и `/BIN`, желательно `/TMP`;
* `/SYS` должен содержать как минимум `esxdos.sys`, `nmi.sys`, `errmsg.ko`, `bdir.ko`, `bfile.ko`,
  `tape.ko` (`esxdos080/docs/readme.txt:33`); версия 0.8.9 добавляет `vdisk.ko`, `betadisk.sys`,
  `trdos*.ko` — их состав видно прямо в нашем рабочем образе (`hdd.hdf`, каталог `/SYS`:
  `NMI.SYS, ERRMSG.KO, TRDOS54T.KO, BFILE.KO, NMI_HELP.SCR, BDIR.KO, ESXDOS.SYS, BETADISK.SYS,
  TRDBOOT.BIN, VDISK.KO, TAPE.KO`);
* «If you want to cold boot/reinit devices, press reset while holding space»
  (`esxdos080/docs/readme.txt:47`) — то есть перебор носителей делается сбросом с зажатым пробелом,
  а не сам собой;
* диски именуются по типу и номеру раздела: первый жёсткий диск, первый раздел = `hd0`.

Ошибочные ответы, которые esxDOS печатает и которые стоит знать при отладке: `No SYSTEM`,
`Mounting drives...`, `ESXDOS error <n>`, `Too many OPEN FILE` (строки внутри `ESXMMC.BIN`, версия
0.8.9).

# 5. ЧЕГО МЫ НЕ ЗНАЕМ (проверяется только опытом)

## General Sound
1. **Что реально стоит в битах 6..1 слова состояния настоящей карты.** Документация: «не
   определены». Обе современные ПЛИС-реализации отдают единицы. Есть ли софт, который на это
   опирается, — неизвестно. Проверяется только на живом железе.
2. **Как настоящая карта отвечает на `#55`/`#AA` без загрузчика NeoGS.** У нас gs105 получит их как
   неизвестные команды. Что делает интерпретатор gs105 с неизвестным кодом — из документации не
   следует.
3. **Точные тайминги, на которые опирается софт в местах `<PAUSE>`** (`#14`, `#15`, `#17`). «Кадра
   два-три» — это 40-60 мс на реальном Спектруме; сколько из этого действительно нужно карте,
   документация не говорит.
4. **Номера переменных команды `#22`** — автор прямо отказался их приводить («вследствие
   несистематизированности и отрывочности данных»).
5. **Каких значений `#23` ждут остальные плееры.** Мы знаем про Mod Player v2.5 (`CP 3`) и
   X-Player (индекс страницы 3). Остальной софт не опрошен.
6. **Требуется ли `#D0`** (в `#B0-#F0` объявлен резерв, а `#D1`/`#D2` там живут). Есть ли команда
   `#D0` и что она делает — не нашлось ни в одном источнике.

## NEMO-IDE и ATA
7. **Есть ли у NEMO линия INTRQ и работает ли nIEN.** Ни в схеме, ни в `EVOPORT` прерывание от
   диска не видно; но драйверы могут его ожидать.
8. **Что настоящий NEMO отдаёт на портах группы CS1, кроме `#C8`.** `EVOPORT` их декодирует,
   `UNREAL` отвечает `0xFF` на все, кроме `#C8`.
9. **Что делает настоящий диск с портом `#11`, если хост читает его без предшествующего `#10`.**
   У нас — отдаёт старую защёлку; настоящая внешняя защёлка вела бы себя так же, но не проверено.
10. **Использует ли реальный ZX-софт CHS-адресацию.** Все известные нам драйверы ходят по LBA, но
    поле `#D0` бит 6 они всё равно выставляют — надо снять трассу с настоящей программы, которая
    ставит его в 0.
11. **Почему Proteus не показывает раздел типа `0x06`.** Гипотезы: не умеет FAT16 / требует признак
    LBA у типа раздела. Различить можно только опытом (у нас для этого есть подмена типа под
    `gs_ctl = 8`).
12. **Обязателен ли декремент Sector Count.** По спецификации — да. Ломается ли на этом конкретный
    ZX-драйвер — не проверено.

## Разметка
13. **Читает ли esxDOS раздел, начинающийся не с LBA 63.** Все наши образы выровнены одинаково.
14. **Насколько велик может быть раздел** до того, как ZX-драйверы начнут переполняться. У нас
    испытаны 67 МБ и 293 МБ.
15. **Работает ли кластер 512 байт** на большом томе с реальным ZX-софтом (наш `hdd32.hdf`).
16. **Пишет ли esxDOS в наш синтезированный том корректно**, если каталог и таблица размещения
    наши — механизм отказа при форматировании спроектирован, но на живом esxDOS не проверен.

## DivMMC
17. **Какой именно набор команд SPI шлёт esxDOS при инициализации** — читается только дизассемблером
    `ESXMMC.BIN` либо трассой на железе.
18. **Что esxDOS делает с CSD/CID** и требует ли конкретных полей (ёмкость мы обязаны сообщить, но
    формат CSD v1 против v2 не выбран).
19. **Нужна ли поддержка многоблочных CMD18/CMD25**, или хватит одиночных CMD17/CMD24.
20. **Как esxDOS реагирует на отказ записи** (наша защита от форматирования): честной ошибкой
    пользователю или порчей своего состояния.

# 6. ГДЕ МЫ ОТСТУПАЕМ ОТ СТАНДАРТА

Перечень честный: каждое место — это «эталон говорит одно, наш код делает другое».

## Известные три

**О-1. Восьмибитные образы обслуживаются неверно.**
Эталон (`LSIDE` `ide.c:446-457`): из файла читается **256** байт, они раскладываются по чётным
байтам логического сектора, нечётные заполняются `0xFF`.
У нас (`НАШЕ` `loader_main.c:6848`): смещение считается верно
(`off = data0 + lba * (g_ide_8bit ? 256 : 512)`), но дальше `f_read(&g_ide_f, g_ide_sec, 512, &br)`
читает **512 байт подряд** и отдаёт их машине как есть. То есть машина получает два сектора
восьмибитного образа, слепленных в один, а старших байтов не получает вовсе. Признак `g_ide_8bit`
при этом честно вычислен (`loader_main.c:6729`) и даже попадает в трассу (бит 1 флагов,
`loader_main.c:6997`) — но на данные не влияет.

**О-2. Бит режима адресации не проверяется.**
Эталон (`LSIDE` `ide.c:653`): `if (chn->head & 0x40)` — LBA, иначе CHS с пересчётом по геометрии и
сектором, считаемым с единицы.
У нас (`НАШЕ` `loader_main.c:6987`): `lba = (st & 0xFF) | (a2 & 0x00FFFF00) | (((a2>>24) & 0x0F) << 24);`
— адрес всегда собирается как линейный, бит 6 регистра `#D0` в разборе не участвует. Хост, пришедший
в CHS-режиме, получит сектор по неверному адресу (и, что хуже, молча).

**О-3. Геометрия из заголовка образа выбрасывается.**
Эталон (`LSIDE` `ide.c:241-247`): цилиндры/головки/секторы берутся из блока IDENTIFY заголовка HDF
(слова 1, 3, 6) и потом используются и в CHS-пересчёте, и в вычислении ёмкости.
У нас (`НАШЕ` `loader_main.c:6730-6766`): IDENTIFY **синтезируется целиком**, геометрия жёстко
`16 головок × 63 сектора`, цилиндры = `secs/(16·63)` с ограничением 16383. Обоснование в коде —
«у настоящих образов блок почти весь нулевой (измерено на divide.hdf), а драйвер по нему решает,
есть ли диск». Обоснование верное для нулевого блока, но у образа с заполненным блоком мы всё равно
выкинем его геометрию. Команда `0x91 INITIALIZE DEVICE PARAMETERS` тоже только **запоминает**
геометрию (`loader_main.c:7059-7064`) и никуда её не применяет.

## Найденные при этой сверке

**О-4. Дешифратор портов ловит лишнее (`A3 = 0, A4 = 0`).**
Эталон `EVOPORT` (`zports.v:338`): `ide_even = (loa[2:0]==3'b000) && (loa[3] != loa[4])` — оба
chip select одновременно активными быть не могут. `UNREAL` (`io.cpp:501`): `if ((port & 0x18) != 0x10)
return 0xFF; // invalid CS0,CS1`.
У нас (`nemo_ide.v:82`): `cs0 = ebl & ~a[3]`, без условия на A4. Значит порты `#00, #20, #40, #60,
#80, #A0, #C0, #E0` (и их варианты с A0=1) декодируются как регистры CS0, а `sup = ebl`
(`nemo_ide.v:87`) при этом ещё и **давит внутренний декодер машины** на всём окне, включая адреса,
на которые мы не отвечаем (`A3=1, A4=1`: `#18, #38, #58, #78, #98, #B8, #D8, #F8`).

**О-5. Младший бит адреса используется как признак защёлки на всех регистрах.**
Эталон `EVOPORT` (`zports.v:339`): старшая защёлка — **ровно порт `#11`** (`loa == NIDE11`), а все
регистровые порты требуют `loa[2:0] == 000`. У нас `hi = a[0]` (`nemo_ide.v:84`) без привязки к
номеру регистра, то есть `#31, #51, #71, #91, #B1, #D1, #F1` тоже читаются как старшая защёлка.

**О-6. Группа CS1 отвечает состоянием на любой номер регистра.**
`UNREAL` отвечает только на `#C8` (`(port & 0xE0) == 0xC0`), остальные CS1-порты дают `0xFF`
(`io.cpp:1274`). У нас `if (cs1) q = st_mach;` (`nemo_ide.v:251`) — состояние отдаётся по всем
восьми адресам группы. По ATA в блоке управления вообще есть только регистр 6 (Alt Status/Device
Control) и 7 (Drive Address).

**О-7. Sector Count не декрементируется, адресные регистры не продвигаются.**
Эталон `LSIDE` `ide.c:687-723`. У нас регистр `#50` пишет только хост (`nemo_ide.v:290`), а ARM
считает блоки в своей переменной `g_ide_rd_rem` (`loader_main.c:6596`). После многосекторного чтения
файл регистров хранит **исходный** адрес и **исходный** счётчик, тогда как драйвер вправе прочитать
оттуда адрес последнего переданного сектора.

**О-8. Регистр ошибки урезан до четырёх бит.**
`nemo_push` отдаёт в фабрику `g_nemo_err & 0x0F` (`loader_main.c:6613`). ABRT (`0x04`) и IDNF
(`0x10`) — по разные стороны границы: **IDNF, UNC (`0x40`) и BBK (`0x80`) сообщить нечем**. Между
тем `LSIDE` на выход за границу диска отвечает именно `ABRT | IDNF` (`ide.c:680`), а на сбой чтения
— `ABRT | UNC` (`ide.c:793`).

**О-9. Неизвестная команда отвергается без кода ABRT.**
У нас `else { nemo_push(0x51u, 0, 0, 0); }` (`loader_main.c:7079`) — ERR поднят, а регистр ошибки
остаётся нулём (`g_nemo_err` обнулён предыдущим ответом). По ATA неподдержанная команда обязана
дать `ERR` **и** `ABRT` в регистре ошибки.

**О-10. `0xC6 SET MULTIPLE MODE` квитируется, но не реализован.**
`loader_main.c:7076-7078` отвечает `0x50` на `0xE7, 0x08, 0xEF, 0xC6, 0xE0, 0xE1`. Драйвер, увидев
успех `0xC6`, вправе выдать `0xC4 READ MULTIPLE`, а её мы отвергаем. Либо реализовать, либо отвечать
на `0xC6` ошибкой.

**О-11. Команды записи не реализованы вовсе.**
`0x30/0x31 WRITE SECTOR(S)` попадают в `else` и получают ERR. Образ открывается только на чтение
(`f_open(..., FA_READ)`, `loader_main.c:6721`). Для esxDOS с его «FAT16/FAT32 read/**write**» это
принципиальное ограничение, а не мелочь.

**О-12. Регистр состояния один на два устройства.**
В фабрике статус живёт один (`nemo_ide.v:220`), и признак выбранного устройства в него не входит.
Прошивка обходит это, переиздавая статус при каждой смене выбора (`loader_main.c:6975-6976` и `loader_main.c:7091`), но окно между probe slave и следующим чтением статуса master остаётся принципиально
негерметичным.

**О-13. Заголовок HDF версии 1.1 разбирается только частично.**
Мы читаем подпись (и то по четырём байтам `RS-I`, а не по шести плюс `0x1A`, как `LSIDE`
`ide.c:224`), флаги и смещение данных, а поля версии (`0x07`) и резерв не проверяем вовсе
(`loader_main.c:6717-6730`). Образ версии 1.0 со смещением `0x0080` у нас откроется, но блок
IDENTIFY в нём 106 байт, а не 512 — и разницы мы не заметим, потому что блок всё равно не читаем
(см. О-3).

**О-14. Порт `#33` NeoGS не реализован.**
Наш трап декодирует ровно `#BB` и `#B3` (`sources/atlas_core/main.v:515-516`). Софт, рассчитанный
на NeoGS, начинает с `OUT (#33),#80` (`NGSLOAD`) и дальше действует по правилам загрузчика, а не
штатной прошивки. Это не «отступление от GS», а **отсутствие NeoGS-совместимости** — но софт
различает карты именно по этому.

**О-15. Загрузчика прошивки нет.**
Ни NeoGS-загрузчика (команды `#00`-`#0B`, `NGSLOAD`), ни собственного пути замены прошивки карты у
нас нет: карта поднимается на `assets_gs105b.rom` и только на нём (`GENERAL_SOUND.md:22`). Команды
`#13`/`#14`/`#15` оригинального GS при этом работают по построению — их исполняет настоящая
прошивка на эмулируемом Z80.

**О-16. DivMMC в фабрике отсутствует.**
Готова только сторона ARM — синтез тома FAT16 из папки (`arm/divmmc_fs.c`, 825 строк,
`arm/divmmc_fs.h`). Ни ловушек адресов, ни портов `#E3/#E7/#EB`, ни SPI-сдвигателя в исходниках
ПЛИС нет (`grep -i divmmc sources/*.v` даёт единственное упоминание в комментарии
`atlas_core/memory.v:125`). То есть раздел 4 этого документа — спецификация того, что предстоит
сделать, а не описание того, что есть.

**О-17. Синтезированный том использует кластер 32 КБ и 2048 записей корня.**
`arm/divmmc_fs.h:36-37`: `DMFS_ROOTENT 2048`, `DMFS_SPC 64` (32 КБ). `FATGEN` формально это
позволяет (`SecPerClus = 64` при 512 байтах в секторе даёт ровно 32 КБ, потолок спецификации), а
`BPB_RootEntCnt` у FAT16 рекомендован 512. То есть мы стоим на самой границе допустимого в обоих
полях. В самом файле это отмечено как осознанный выбор с планом отката.

## П.1 GENERAL SOUND: у карты ДВА протокола, а не один

Кроме штатной прошивки у NeoGS есть **загрузчик**, и он слушает те же порты. Официальный текст —
`refs/gs/docs/neogs_loader_v021.txt` («Загрузчик для NeoGS v0.21»), исходник —
`refs/gs/src/loader_ngs.a80`.

**Вход в загрузчик:**

```
LD A,#80 : OUT (GSCTR),A   ; сброс NeoGS  (GSCTR = порт #33)
NOP NOP NOP                ; ждём 12 тактов
LD A,#55 : OUT (GSDAT),A : OUT (GSCOM),A : CALL WC
LD A,#AA : OUT (GSDAT),A : OUT (GSCOM),A : CALL WC   ; второго сброса ждать ДОЛЬШЕ:
                                                     ; переносится код загрузчика из ПЗУ в ОЗУ
```

Байт пишется **в оба порта**, и загрузчик требует их РАВЕНСТВА
(`refs/gs/src/loader_ngs.a80.utf8.txt:39-47`):

```
RDBYT01  IN A,(ZXCMD)  : LD C,A
         IN A,(ZXDATRD): OUT (CLRCBIT),A
         CP C          : JR NZ,RDBYT03   ; не совпали — грузим штатную прошивку
         CP 0x55       : JR NZ,RDBYT03
```

**Окно ожидания — ровно 256 итераций `DJNZ`** (`LD B,0` … `DJNZ .L1` … `DEC B` → `JR RDBYT03`).
Не уложился — карта молча уходит в штатную прошивку. Второй байт ждётся тем же счётчиком.

Команды загрузчика (полный список с примерами кода — в `neogs_loader_v021.txt`):
`#00` принять 32 КБ прошивки со Спектрума в страницу 0, `#01` запустить её (ставит защиту от записи
и 20 МГц), `#02` штатная прошивка из ПЗУ, `#03` прошивка с SD (`NEOGS.ROM` в корне, только короткие
имена), `#04` загрузить код в произвольную страницу по `#8000`, `#05` загрузить файл с SD по пути
`DIR1/DIR2/FILE.EXT` (только верхний регистр), `#06` запустить код по адресу в странице,
`#07` статус последнего файла (`#00` ок, `#AA` не найден, `#DD` нет FAT, `#EE` нет SD),
`#08` текстовая версия страницы, `#09` CRC16, `#0A` файл обновления `NGS_ROM.UPD`,
`#0B` частота процессора (0=10, 1=12, 2=20, 3=24 МГц; бит7 — прочитать текущую).
**Все прочие коды перезапускают NeoGS со штатной прошивкой.**

Подпрограммы ожидания у загрузчика те же, что у штатной прошивки:

```
WC  IN A,(GSCOM) : RRCA : JR C,WC : RET      ; ждать снятия command bit
WD  IN A,(GSCOM) : RLCA : JR C,WD : RET      ; ждать готовности принять данные
WN  IN A,(GSCOM) : RLCA : JR NC,WN : RET     ; ждать появления данных
```

## П.2 Команда `#1D` — это peek по `#20XX`, а «сигнатура GS» `#8B` — просто байт прошивки

`refs/gs/src/main_ngs.a80.utf8.txt:874-880`:

```
COM1D  IN A,(ZXDATRD) : LD L,A : LD H,0x20 : LD A,(HL)
       OUT (ZXDATWR),A : OUT (CLRCBIT),A : JP COMINT_
```

То есть команда отдаёт байт памяти карты по адресу `0x2000 + параметр`. Дока загрузчика:
«Предназначена для проверки загрузчик ли сейчас на NeoGS. По этой команде возвращает через порт
данных число `#76`. Для примера: стандартная прошивка возвращает значение `#8B`, мой MP3 плеер
возвращает `#77`».

**Проверено на дампах** (`refs/gs/roms/`): байт по `0x2000` равен `0x8B` в `gs104`, `gs105a`,
`gs105b`, `gs108`, `neogs` — и в нашем `assets_gs105b.rom` тоже. Значит детект карты у плееров = чтение
ЧУЖОЙ ПАМЯТИ, и любая эмуляция без настоящих байтов прошивки по `0x2000` его не проходит. У нас
проходит по построению (крутится настоящая прошивка).

## П.3 Неизвестная команда штатную прошивку НЕ вешает — гипотеза «карта не ответила на #55» закрыта

Диспетчер (`refs/gs/src/COM_L.a80:1-50`):

```
COMHZ    OUT (RSCOM),A          ; <-- снятие command bit ПЕРВЫМ ДЕЙСТВИЕМ
COMINT   LD SP,ISTACK
COMINT1  IN A,(COMRG) : CP #20 : JR C,COMLOW
COMINT2  CP #F0 : JR C,COMHIGH : SUB #D0     ; #F0..#FF -> индексы #20..#2F в COMTAB
```

Таблица `COMTABH` (`refs/gs/src/TABLES_H.a80:10+`) покрывает `#20..#EF`; определены
`#20-#23, #2A-#2F, #30-#3F, #40-#42, #45-#49, #50, #60-#69`, весь блок `#80-#9F` (→ `COM80`) и
`#A0-#AF` (→ `COMA0`). **Всё остальное — `COMHZ`.** Коды `#55` и `#AA` попадают именно туда, а
`COMHZ` первым же тактом делает `OUT (RSCOM),A`, то есть command bit снимается немедленно.

Следствие для нас: если плеер шлёт NeoGS-рукопожатие карте со ШТАТНОЙ прошивкой, `CALL WC`
возвращается сразу на обоих байтах — плеер решает, что загрузчик жив, и продолжает слать ему
команды `#00`/`#01`, которые штатная прошивка трактует совсем иначе. Зависание при этом наступает
не на рукопожатии, а на следующем шаге. Проверять надо именно продолжение диалога.

## П.4 Регистр данных и регистр вывода — ФИЗИЧЕСКИ РАЗНЫЕ ячейки

`refs/gs/docs/gs_prog.txt` (раздел 4): «Несмотря на то, что регистр данных и регистр вывода
расположены в пространстве адресов портов по одному и тому же адресу и воздействуют на один и тот же
бит данных, они являются двумя независимыми регистрами. Значение, один раз записанное в один из этих
регистров, остается неизменным в нем до новой записи». Там же: «Command bit … сбрасываться в 0 он
может только из GS». MAME реализует это буквально (`refs/gs/src/mame_neogs.cpp`: `m_data_in` /
`m_data_out`, а неопределённые биты статуса отдаются единицами — `return m_status | 0x7e;`).

Из `refs/gs/docs/ngspgm_01a.txt`: «Перед началом обмена потоком байт установите бит данных в
подходящее для начала обмена состояние… Установка бита данных производится **холостым обращением**
к порту ZXDATWR или ZXDATRD». То есть холостое чтение/запись ОБЯЗАНО менять data bit, иначе поток
стартует в неверной фазе.

Порт `#33` (GSCTR) по `refs/gs/docs/ports.inc`: `C_GRST=#80` (сброс), **`C_GNMI=#40`** (NMI на Z80
карты), `C_GLED=#20`.

## П.5 Что видно в самом Z-Player 4.1 (без платы)

Каталог образа — `refs/gs/zplayer41/zplay41_trd_catalog.txt`. Тело плеера `ZPLAY4.1.B` лежит с
offset `0x1900`, 80 секторов (40 КБ), и **не упаковано** (нормальная плотность `CD`/`21`, читаемый
пролог `76 F3 31 FF 6C …`). В этих 40 КБ **нет ни одного байта `D3 33` или `DB 33`** — то есть порт
`#33` плеер, судя по всему, не трогает вовсе; прямые обращения есть только к `#BB`/`#B3`
(`OUT (#BB)`, `IN (#BB)` ×2, `OUT (#B3)`), плюс есть косвенные `LD BC,#xxB3` / `LD BC,#xxBB`.
Оговорка: сканирование байт — не дизассемблирование, окончательный вывод даёт только разбор кода,
но файл для этого готов и лежит в `refs/`.

Официальный readme плеера (`refs/gs/zplayer41/zp41_readme.txt`, 23.01.2023) существен сам по себе:

- HDD и SD — **только MS-DOS/FAT32**, до 4 primary разделов на носитель; FDD — TR-DOS и FAT12;
- интерфейсы: ATM-IDE, **NEMO-IDE**, SMUC v1/v2, DivMMC, Z-Controller;
- «Пользователям Scorpion GMX необходимо **отключить NEMO-IDE** в настройках»;
- «Пользователям DivMMC необходимо включить DivMMC в настройках»;
- «Чтобы попасть в настройки, **удерживайте “Enter” во время загрузки**».

История версий (`version_history.txt`) для 4.1: «корректировки в FAT32 драйвере», «корректировки в
DivMMC драйвере», «**добавлена возможность ручного выбора GS загрузчика**». Последнее означает, что
автоопределение загрузчика ломается на нестандартных картах и в плеере предусмотрен ручной обход —
это проверяется прямо на плате, без единой правки кода.

## П.6 NEMO-IDE: Wild Commander читает НАЧАЛО раздела правильно (+8)

Разбор `refs/ide/wc/CORE32.ASM:1341-1390` по шагам:

```
1341  LD A,3,(COUNT),A,(ZES),A
1343  LD HL,LOBU+446+4, DE,16, B,4      ; HL смотрит на байт ТИПА записи 0
1344  KKO  LD A,(HL)
      CP #05 / #0B / #0C / #0F : JR Z,OKK
      ADD HL,DE : DJNZ KKO              ; 4 записи по 16 байт
1379  OKK  INC HL,HL,HL,HL              ; +4 -> запись+8 = НАЧАЛО раздела
      LD E,(HL):INC HL : LD D,(HL):INC HL : LD A,(HL):INC HL : LD H,(HL),L,A : EX DE,HL
```

То есть HL:DE = 32-битный `start_sect` из байтов +8..+11 — ровно как у FatFs (`PTE_StLba 8`),
hdfmonkey (`refs/ide/hdf/hdfmonkey_mbr.c`) и ядра Linux (`refs/ide/part/linux_partitions_msdos.c`).
**Ошибки «взял размер вместо начала» в исходнике Wild Commander нет.** Значит наш симптом надо
объяснять не арифметикой плеера, а тем, ЧТО он у нас читает и по какой ветке уходит.

## П.7 Wild Commander принимает только FAT32 — и на не-FAT32 диске ЗАЦИКЛИВАЕТСЯ

Сразу после поиска раздела (`CORE32.ASM:1386-1400`) идёт жёсткая проверка BPB:

| смещение | что | требование |
|----------|-----|------------|
| +11 | байт на сектор | ровно 512 (`LD A,H : DEC A,A : OR L`) |
| +13 | секторов на кластер | ≠ 0 **и степень двойки** |
| +14 | зарезервированных | ≠ 0 |
| +16 | копий FAT | ≠ 0 |
| +17 | записей корня | **обязан быть 0** (это FAT32) |
| +22 | FATSz16 | **обязан быть 0** |
| +36 | FATSz32 | ≠ 0 |

Типы разделов в поиске — только `#05`, `#0B`, `#0C`, `#0F`. **FAT16 (`#04`/`#06`/`#0E`) не
поддерживается вовсе.**

Что происходит на диске без FAT32-раздела (важное для нас):

1. цикл `KKO` не находит тип → проваливается в `FHDD`;
2. `FHDD` при `ZES≠0` перечитывает сектор 0 и требует, чтобы **вторая запись таблицы**
   (`LOBU+446+16`, 16 байт) была вся нулевая, иначе `JP NZ,NHDD`;
3. счётчик `COUNT` (3) исчерпывается → `NHDD`: база обнуляется, `ZES=0`, переход на `LDBPB`;
4. `LDBPB` читает **сектор 0 как BPB** — проверки не проходят → `JP NZ,FHDD`;
5. `FHDD` при `ZES=0` → `JP Z,NHDD` → `NHDD` → `LDBPB` → …

Ветки 4-5 замкнуты друг на друга: на диске без FAT32-раздела код **бесконечно перечитывает сектор 0
и разбирает MBR как загрузочный сектор**. Внешне это и есть «промахнулся мимо файловой системы»
(а также «завис при живом диске»).

Наши образы (проверено байтами на ThinkPad):

| файл | тип раздела | start | секторов | BPB |
|------|-------------|-------|----------|-----|
| `/tmp/hdd.hdf`, `/tmp/divide.hdf`, `/tmp/oleg.hdf` | **`06` FAT16** | 63 | 131009 | spc=4, rootent=512, FATSz16=128 |
| `/tmp/hdd32.hdf` | `0C` FAT32 | 63 | 131009 | spc=1, rootent=0, FATSz32=1008 |
| `/tmp/hdd32b.hdf` | `0C` FAT32 | 63 | 573489 | spc=8, rootent=0, FATSz32=559 |

Прошивка синтезирует то же самое: `arm/divmmc_fs.c:595` — `p[4] = 0x06;` с комментарием «FAT16
больше 32 МБ — именно его ищет esxDOS». Для esxDOS это верно, для Wild Commander и Z-Player —
дисквалификация носителя. Из трёх образов требованиям Wild Commander удовлетворяет только
`hdd32b.hdf` (тип `0C`, rootent=0, FATSz16=0, FATSz32≠0, spc=8 — степень двойки).

## П.8 Обмен по NEMO: чего требует эталонный драйвер

`refs/ide/wc/IDE_NEMO.ASM`:

- сектор читается строго парами `LD C,#10 : INI` / `LD C,#11 : INI` ×256 — то есть **`#11` обязан
  отдавать старший байт слова, защёлкнутый при чтении `#10`**; сбой фазы = каждый второй байт мусор
  и все 32-битные поля MBR/BPB битые;
- путь DMA (TS-Labs) выбирается, когда `IN (#AF) AND %11 == 0`; неотвеченный порт `#AF`, читающийся
  как `0x00`, уводит драйвер в несуществующий DMA (у нас `#AF` не декодируется — держать в уме);
- LBA28: `DRVRE` = `#E0`/`#F0` (старший ниббл LBA в Drive/Head), команды `#20` чтение, `#30` запись,
  `#EC` IDENTIFY.

## П.9 Три несовместимые разметки ZX-диска

- **MBR** — Wild Commander, esxDOS, FatFs, hdfmonkey (`start_sect` +8, `nr_sects` +12, LE32,
  сигнатура `55 AA`; hdfmonkey вдобавок считает раздел файловым только при `status == 0x80`).
- **IDEDOS / PLUSIDEDOS** (`refs/ide/idedos/zxvgs_idedos.txt`) — запись **64 байта**: тип на +16,
  начальный ЦИЛИНДР на +17, головка +19, а на +23 «Largest logical sector number», то есть РАЗМЕР;
  линейного начала в записи нет вовсе. Там же — детект 8-битного интерфейса по подписи
  `"P?L?U?S?I?D?E?D?O?S"`, что соответствует биту 0 по смещению `0x08` в HDF («halved sector data»).
- **iS-DOS / Nemo** (`refs/ide/nemo/zxpress_4082_isdos_nemo.txt`, ZX Format #05) — таблицы на диске
  НЕТ вообще: начальные дорожки устройств A..H прописываются в самом драйвере утилитой
  `ide_tune.com`, максимум 16 МБ на устройство.
- Для совместного диска +3e (`refs/ide/idedos/plus3e_sharingdisks.txt`): первый первичный раздел —
  с типом, не используемым PC (в примере `0x7F`), начало с блока 1, FAT-раздел — `0x0E`.

HDF-заголовок наших образов проверен: `"RS-IDE"`, ревизия `0x11`, **флаги `0x00`** (полные 16-битные
сектора, не «половинные»), смещение данных `0x216`.

## П.10 DivMMC: автомаппер задан ФАЗОЙ ЦИКЛА, а не адресом

`refs/divmmc/hw/Divide_pgm_model.txt` (оригинал Pavel Cimbal):

> Automatic mapping occurs at the begining of *refresh cycle* after fetching opcodes (M1 cycle) from
> 0000h, 0008h, 0038h, 0066h, 04c6h and 0562h. It's also mapped *instantly* (100ns after /MREQ…)
> after executing opcode from area 3d00..3dffh. Memory is automatically disconnected in refresh cycle
> of the instruction fetch from so called off-area, which is 1ff8-1fffh.

MiSTer делает буквально это (`refs/divmmc/fpga/mister_divmmc.v`): `if(~nRFSH) automap <= m1_trigger;`
и `16'h3DXX: {automap, m1_trigger} <= 2'b11;`. Маппинг «сразу по адресу» ломает вложенные вызовы и NMI.

Оттуда же приоритет и липкость: «The meaning-priority is (from lowest to highest) EPROM jumper ->
MAPRAM -> CONMEM»; «Bit MAPRAM can be set to '1' only (when it's '1', only power-on can return it to
'0')». Расширение Pratto (`refs/divmmc/hw/Divmmc_allram_manual.txt`) даёт выход без снятия питания:
«if mapram is set, now writing to port $E3/227 with %11XXXXXX resets mapram and set conmem», и там же
«Nmi button is disabled when conmem is active». Наш аналог «холодного старта» обязан быть, иначе ПЗУ
не перезалить.

## П.11 esxDOS: требования к носителю и к ПЗУ

`refs/divmmc/esxdos/README_089.TXT`:

- «Full FAT16/FAT32 read/write support (**no 64K clusters, no extended partitions, no LFN**)»;
- «Needs system file `ESXDOS.SYS` in the rootdir of the **first detected drive**»; всё содержимое —
  в корень **первого раздела**;
- «BIOS: Version of system file isn't checked against the ROM version (**bad things will happen if
  there's a mismatch**)» — версия `ESXDOS.SYS` обязана совпадать с версией нашего ПЗУ.

`refs/divmmc/esxdos/esxdos_api.txt`: носитель адресуется полем minor в Device Path — `000` = RAW
(весь носитель), `001` = первый раздел/сессия. То есть софт получает у ядра ЛИБО весь носитель, ЛИБО
раздел, третьего нет.

Проброс папки дешевле синтеза ФС: ZEsarUX (`refs/divmmc/passthrough/zesarux_esxdos_handler.c`) не
синтезирует FAT вообще — он подменяет весь `RST $08` и обслуживает вызовы из хостового каталога.
Гоча оттуда же: параметры приходят в разных регистрах в зависимости от того, откуда звали — при
вызове из ОЗУ вместо `HL` используется `IX` (`if (reg_pc>16383) registro_parametros_hl_ix=&reg_ix;`).
Если понадобится всё-таки блочный уровень (для чужих ПЗУ) — эталоны `qemu_vvfat.c` (полный синтез
MBR+FAT из каталога, R/W) и `mister_sd_card.sv` (виртуальная SD в фабрике).
