# Веб-КВМ НА ПЛАТЕ: что уже сделано и что из этого следует для шага 16

**Дата:** 2026-08-05. **Повод:** владелец уехал от платы, а запись в TR-DOS надо проверять руками -
нужен экран и клавиатура через браузер. Полный КВМ остаётся шагом 16, здесь - минимум для проверки
и, что важнее, снятые неизвестные.

Прежняя реализация разобрана в `WEBKVM_RECOVERED.md` (исходники погибли вместе с ВМ, восстановлены из
собранного ELF). Здесь - новая, на **нулевом** ядре, в общей прошивке.

## Решение: Ethernet ОПРОСОМ, без прерываний

Прежний КВМ жил на core1 - и это было разумно: `xemacpsif_dma.c` из порта lwIP написан под XScuGic,
а на core0 крутится главный цикл, от такта которого зависят лента, дисковод и звук.

Но AMP не понадобился. Обработчики порта - **обычные публичные функции**, а не только тела ISR:

```c
void emacps_recv_handler(void* arg);   /* xemacpsif_dma.c:496 */
void emacps_send_handler(void* arg);   /* xemacpsif_dma.c:289 */
```

Значит их можно звать из главного цикла: они читают статус DMA и разбирают дескрипторы, опрос для
этого годится. Ничто не прерывает цикл - тайминг остаётся ровно таким, каким был. Плата за это -
пропускная способность ограничена частотой цикла; для меню и набора текста этого достаточно.

### 🥇 Гоча, из-за которой умерла плата: порт ВКЛЮЧАЕТ линию GIC сам

`xemac_add` внутри `init_dma` безусловно делает `XScuGic_EnableIntr` для GEM0
(`xemacpsif_dma.c:818`). Спрашивать нас он не собирается. А GIC у прошивки **поднят** (там живёт
ленточный ISR), обработчика GEM0 нет - и первое же завершение передачи (DHCP-запрос уходит сразу)
уводит процессор в `Xil_ExceptionNullHandler`.

Лечится штатной же функцией порта, сразу после подъёма:

```c
emac_disable_intr();   /* мы опрашиваем, значит линия GEM0 в GIC должна быть погашена */
```

## Сеть поднимается ПО КОМАНДЕ, а не на старте (v0.15.234)

Первая версия звала `net_init()` в загрузке. После неудачи стало ясно, что так нельзя: непроверенный
подъём сети не имеет права стоять между включением платы и работающим навигатором - у владельца может
не быть возможности переставить карту.

Теперь это **fs-команда 13 (NET START)**: `net_init()` возвращает слово статуса (бит0 = слушаем,
старший байт = код отказа), команда отдаёт его в `n` и в `err`. Загрузка платы не меняется вовсе.

## Что отдаёт сервер

| Путь | Что |
|---|---|
| `/` | страница: канва, дозагрузка кадра, отправка клавиш |
| `/frame` | СЫРОЙ кадр машины из DDR `0x0FF00000` (ZX 384x302 4bpp = 57984 Б; NES 256x240 8bpp) |
| `/osd` | канва навигатора `0x0F800000`, 640x400 ARGB |
| `/api/key?c=<скан-код>&r=<0/1>` | клавиша в очередь инжекта (то же, что fs cmd 11) |
| `/info` | размер кадра и VERSION ядра |

Размер кадра выбирается по живому `MACHINE_ID` (`GP0+0x60`, `[15:0]==0x5A58` = семейство ZX), поэтому
ZX и NES обслуживаются одним кодом.

**Кадр не сжимается и не копируется:** `tcp_write(..., copy=0)` прямо из DDR. Это и есть причина
высокого FPS у прежней реализации - ARM не тратит такты на кодирование.

### Гоча раздачи: заголовок нельзя гнать через тот же дозатор

Тело больше окна отправки, поэтому раздача идёт куском с продолжением в колбэке `sent`. Если гнать
через этот же дозатор ещё и HTTP-заголовок, то после его отправки `left` обнуляется и соединение
закрывается - тело уходит в закрытый сокет. Заголовок надо писать копией (`TCP_WRITE_FLAG_COPY`)
и только потом ставить тело.

## Состояние сети видно по JTAG

Мейлбокс, некешируемое окно: `KMB+0x60` = статус (бит0 слушаем, бит1 адрес получен, старший байт код
отказа), `KMB+0x64` = адрес. То есть подъём сети проверяется без UART и без браузера.

## 🥇 ОЖИВЛЕНИЕ ПЛАТЫ БЕЗ СНЯТИЯ ПИТАНИЯ (оплачено дважды за вечер)

Отдельная находка, полезная далеко за пределами КВМ. **Тёплая загрузка прошивки по JTAG
(`rst -system` + `ps7_init` + `dow`) на этой плате ненадёжна:** во второй раз `dow` сорвался, и вслед
за ним умер отладочный APB - `targets` показывал только

```
1  DAP (APB AP transaction error, DAP status 0x30000021)
2  xc7z010
```

Ядер нет, память через DAP не читается («Context does not support memory read»), то есть и QUIESCE не
записать.

**Помогает `rst -system`, поданный на цель `DAP`.** Ядра возвращаются, BootROM берёт образ с карты,
кадр снова живой (`hpw` растёт). Скрипт: `sources/jtag_revive_dap.tcl`.

Что НЕ работает:
* `rst -por` -> «por not supported for target» (на Zynq-7000 через xsdb POR недоступен);
* `rst -system` на цели `xc7z010` -> «Invalid reset type»;
* доступ к памяти через DAP -> «Unsupported command».

Если пропала вся цепочка - сначала поднять сервер:
`/tools/Xilinx/Vivado_Lab/2023.1/bin/hw_server -s tcp::3121` (он живёт в Vivado_Lab, а не в Vitis).

⚠ Это НЕ лечение полуоткрытого бёрста в S_AXI_HP0 (замёрзший кадр при живом звуке) - там по-прежнему
нужен настоящий POR. Это другой отказ: умерший отладочный APB.

**Следствие для порядка работ:** прошивку проверять с карты (собрать образ, записать мейлбоксом,
тёплая перезагрузка), а не тёплым `dow`. Образ v234 - 1.72 МБ против 1.64 МБ у v232: код lwIP занял
всего ~80 КБ, семисоткилобайтный прирост ELF был отладочными символами.

## Сборка

lwIP **уже собран** в BSP второго ядра, и его архив линкуется в образ нулевого:

```
BSP1=$WS/ebaz/ps7_cortexa9_1/ps7_cortexa9_1/bsp/ps7_cortexa9_1
LWINC="-I$BSP1/include -I$BSP1/include/lwip -I$LW/lwip-2.1.3/src/include -I$LW/contrib/ports/xilinx/include"
... -L"$BSP1/lib" ... -Wl,--start-group,-lxil,-llwip4,-lgcc,-lc,-lm,--end-group
```

Драйвер `XEmacPs` уже лежит в `libxil.a` нулевого ядра - отдельно собирать нечего. Путь
`-I$BSP1/include/lwip` обязателен: `xpqueue.h` включает `debug.h` без префикса каталога.

lwIP сконфигурирован `NO_SYS=1` и `NO_SYS_NO_TIMERS=1`, поэтому таймеры протоколов крутит наш цикл
(`tcp_tmr`, `etharp_tmr`, `dhcp_fine_tmr`, `dhcp_coarse_tmr`).

## 🚧 ГЛАВНОЕ: ПРОВОДА НЕТ БЕЗ НОВОГО БИТСТРИМА

Прошивка со сервером поднимается и слушает 80-й порт, но адреса по DHCP не получает. Причина
измерена, а не угадана:

| Что измерено | Значение |
|---|---|
| `frames_tx` / `frames_rx` (GEM0 0x108 / 0x158) | 0 и 0 при включённых приёме и передаче |
| MDIO, все 32 адреса | нули - ни один PHY не отвечает |
| MIO 16..27, 52/53 (живые) | поля выбора периферии нулевые = обычный GPIO |
| `GEM0_RCLK_CTRL` / `GEM0_CLK_CTRL` | `0x11` / `0x00500141` - такты из **EMIO** |
| проект ПЛИС прежнего КВМ | `C_EN_EMIO_ENET0`, `ENET0_GMII_*` и `ENET0_MDIO_*` наружу как внешние порты, набор `RX_DV`/`TX_EN`/`RX_CLK`/`TX_CLK` = **MII** |

**PHY этой платы висит на выводах ПЛИС, а не на MIO.** Поэтому веб-КВМ невозможно поднять одной
прошивкой: битстрим обязан вывести сигналы GEM0 через EMIO на ноги PHY. Прежний КВМ и работал со
своим битстримом (`ws/ebaz_kvm/hw/design_4_wrapper.bit`) - вот чего не хватало в моей картине, когда
я счёл, что «Ethernet не требует ПЛИС» (тот вывод был сделан по DTS Linux и оказался неверным).

### ⚠ Тупик, который не надо повторять

Замуксовать MIO 16..27 на GEM0 (`L0_SEL=1`) и MDIO на 52/53 (`L3_SEL=4`) из ARM **можно**, и
`frames_tx` даже становится 1, MDIO начинает читать `0xFFFF` вместо нулей (линия ожила). Но провода
от этого не появляется, а **MIO 24/25 - это UART платы** (`L3_SEL=7`, выход и вход), и такая правка
его ломает. Проверено и откатано; в прошивке этого кода сознательно нет.

### Ноги PHY: в наших файлах их НЕ БЫЛО, восстановлены по документации платы

Ни одного `.xdc` с `ENET`/`MDIO` в архивах не сохранилось, в `.xsa` назначений ног тоже нет - они жили
в проекте Vivado внутри погибшей ВМ. Взяты из публичной документации EBAZ4205 и сверены с нашими
ограничениями: **все 15 выводов у нас свободны** (`sources/bulbulator_ddr.xdc` их не занимает).

PHY платы - **IP101GA**, подключён 4-битным MII (в документации ноги подписаны «RMII», но данных по
четыре в каждую сторону плюс свои такты - это MII; и порты прежнего проекта `RX_DV`/`TX_EN` это
подтверждают).

| Сигнал | Нога | Примечание |
|---|---|---|
| TX_EN | W19 | |
| TXD0..TXD3 | W18, Y18, V18, Y19 | |
| TX_CLK | U15 | `IO_L11N_T1_SRCC_34` - тактовая ✅ |
| RX_DV | W16 | |
| RXD0..RXD3 | Y16, V16, V17, Y17 | |
| RX_CLK | U14 | `IO_L11P_T1_SRCC_34` - тактовая ✅ |
| MDC | W15 | |
| MDIO | Y14 | двунаправленный: `ENET0_MDIO_I/O/T` |
| **опорный такт PHY** | **U18** | `IO_L12P_T1_MRCC_34`; сеть платы подписана `CLK_50M_PHY`, но для MII нужны **25 МГц** |

**Опорный такт PHY даёт ПЛИС** - вот почему микросхема молчала на все 32 адреса MDIO: она не только
не подключена к процессору, но и не тактируется. В проекте прежнего КВМ ровно для этого и стоял
`clk_wiz`. Это же объясняет, почему `frames_tx` вырос до 1 при муксе на MIO, а ответа не было: наши
пины что-то передавали, а PHY при этом стоял без такта.

Итого для битстрима: 15 выводов насквозь, 25 МГц на U18, `C_EN_EMIO_ENET0` в блоке PS. Логики
почти нет - это провода; риск только в тактах приёма и передачи, но обе ноги оказались тактовыми.

## Что осталось до шага 16

* **вывести GEM0 через EMIO на ноги PHY в битстриме** - без этого всё остальное бессмысленно.
  Хорошая новость: MII-проброс дёшев по логике (это провода, а не конвейер), дорог он выводами и
  тактами приёма с PHY, которым нужны тактовые ноги; при нынешних 87 % LUT место искать всё равно
  придётся;
* **выключатель**: сеть уже поднимается только по команде 13, второе ядро не занято вовсе (сервер
  живёт на нулевом, опросом) - владельцу это и нужно было, чтобы освобождать ресурсы. Осталось
  добавить строку в меню опций и команду «выключить»;
* проверить подъём (`ping`, адрес по DHCP), затем страницу и клавиатуру на настоящем железе;
* время в `net_poll` считается тактами цикла, а не миллисекундами - для DHCP это грубо, надо привязать
  к настоящему счётчику;
* остальные API прежнего КВМ (`fs`, `launch`, `machine`, `opt`, `net`) - они и так сводятся к
  мейлбоксу, переписывать логику навигатора не придётся;
* звук (владелец просил тот же поток, что уходит в HDMI) - отложен сознательно;
* фронтенд взять из `RECOVERED_UI_FRAGMENTS.txt`, там он полнее нынешней минимальной страницы.
