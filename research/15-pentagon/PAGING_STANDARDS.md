# Стандарты страничности и видеорежимов: Пентагон 1024/«4М», ATM Turbo 2+, мультиколор

Спецификация для реализации. Составлена 09.08.2026 по первоисточникам, а не по нашим догадкам.
Правило владельца дословно: «читай стандарты переключения адресации памяти и просто делай как в
стандартах придумано». Отсюда формат документа:

- каждое утверждение — со ссылкой на источник;
- расхождения между источниками НЕ склеиваются и НЕ сглаживаются: они выписаны, и для каждого
  сказано, какой вариант берём мы и почему;
- всё, что источниками не подтверждено, живёт в разделе «Чего мы НЕ знаем» и подлежит проверке
  софтом на железе, а не изобретению в RTL.

Правило сверки источников (оплачено дефектом `wd1793.sv`): смотреть ЖИВОЙ апстрим по
`raw.githubusercontent.com`, а не вендоренную копию в `cores/` — наша копия может быть старше
оригинала, и нужной строки в ней уже не будет.

Границы документа: это разбор, а не патч. Ни один файл в `sources/` этой работой не трогается.

## 1. Пентагон 1024: канон 1 МБ

### 1.1 Первоисточник

zx-pk.ru, тред 11490 (VELESOFT / Black_Cat, 2009) —
<https://zx-pk.ru/printthread.php?t=11490&pp=40>:

> port 7FFD (01xxxxxx xxxxxx0x): D0..D2 = bank 0..2; D3 videoram; D4 rom; **D5 = bank 5 ;1024 kB
> (if D2 of port EFF7=0); D6 = bank 3 ;256 kB; D7 = bank 4 ;512 kB**.
> port EFF7 (**1110xxxx xxxx0xxx**): D2 = 1 — set 128 kB mode, 0 — enable 1MB; (if D2 of EFF7=1 then
> D5 of 7FFD is used for disable paging); D3 = 1 — disable rom and connect ram page 0 in 0-3FFF.

Отсюда формула:

```
банк[5:0] = { 7FFD[5], 7FFD[7], 7FFD[6], 7FFD[2:0] }
```

512 КБ — только D6 и D7; 256 КБ — только D6.

### 1.2 Четыре независимые реализации дают ровно её

| Источник | Строка |
|---|---|
| Fuse `machines/pentagon1024.c` | `page += ((last_byte & 0xC0) >> 3) + (last_byte & 0x20);` — [raw](https://raw.githubusercontent.com/Toysoft/fuse-emulator-fuse/master/machines/pentagon1024.c) |
| UnrealSpeccy `io.cpp` | `page1024 = (val & 0x20) \| ((val & 0xC0) >> 3) \| (val & 0x07)` — [raw](https://raw.githubusercontent.com/tslabs/zx-evo/master/pentevo/unreal/Unreal/io.cpp) |
| MiSTer `ZX-Spectrum.sv:551` | `page_128k[2:0] <= { cpu_dout[5], cpu_dout[7:6] };` |
| TS-Conf, док | «1024кБ \| `Page3[5:0] = #7FFD[5], #7FFD[7:6], #7FFD[2:0]`» — [tsconf_en.md](https://github.com/tslabs/zx-evo/blob/master/pentevo/docs/TSconf/tsconf_en.md) |

ZEsarUX (`src/mem128.c`) цитирует текст zx-pk дословно, отдельным источником не считается.

### 1.3 Дешифрация EFF7

`A15..A12 = 1110`, `A3 = 0`. Подтверждено трижды: Fuse (`{ 0xf008, 0xe000, …
pentagon1024_v22_memoryport_write }`), MiSTer
(`page_p1024 = addr[15]&addr[14]&addr[13]&~addr[12]&~addr[3]; //eff7`), таблица портов Black_Cat
`#EFF7 … 1110xxxxxxxx0xxx`
([zx-ports-full-table.txt:44](https://raw.githubusercontent.com/tslabs/zx-evo/master/pentevo/docs/ZX/zx-ports-full-table.txt)).
Неполное декодирование — свойство настоящего железа, а не наша экономия.

### 1.4 Остальные биты EFF7

UnrealSpeccy `emul.h:436`: `4BPP 0x01, 512 0x02, LOCKMEM 0x04, ROCACHE 0x08, GIGASCREEN 0x10,
HWMC 0x20, 384 0x40, CMOS 0x80`. Периодика (Alone Coder, Born Dead #10): «bit 2 — защёлка памяти
выше 128k. 0 — есть память, 1 — нет» — <http://zxpress.ru/article.php?id=8701>.

### 1.5 Сброс

Alone Coder там же: «порт #eff7 (дешифрация minimum по A3, A12, IOWR, **сброс по RES**)»;
Fuse `machine_current->ram.last_byte2 = 0;`; MiSTer `page_reg_p1024 <= 0;`. После RESET EFF7 = 0,
то есть машина стартует В МЕГАБАЙТНОМ РЕЖИМЕ.

### 1.6 Бит 5 порта 7FFD

Блокировка страничности только при EFF7[2] = 1. Alone Coder: «Защёлка 48k/non 48k (#7ffd bit 5)
срабатывает лишь в том случае, когда… 2-й бит порта #eff7 установлен»; MiSTer
`page_disable = … | (p1024 & page_reg_p1024[2] & page_reg[5])`.

### 1.7 Что уже сделано у нас — и совпадает с каноном 1:1

`sources/atlas_core/memory.v`:

- `:105` — `if(pent_ext && !port_eff7[2]) page_hi <= {mapOnIORQData[5], mapOnIORQData[7:6]};`
  (та же формула, расширенные биты — ОТДЕЛЬНАЯ защёлка);
- `:74` — `wire page_lock = pent_ext ? (port_eff7[2] & port7FFD[5]) : port7FFD[5];`;
- `:77` — `wire eff7_write = !iorq && !wr && a[15] && a[14] && a[13] && !a[12] && !a[3] && pent_ext;`;
- `:82` — `port_eff7 <= 8'd0;` по сбросу.

**Решение по 1 МБ: не менять ничего.** Реализация совпала с каноном по всем четырём пунктам.

## 2. Расхождения источников по 1 МБ (оставлены видимыми)

### Р-1. Липкость блокировки страничности

- Fuse защёлкивает флаг (`ram.locked = b & 0x20`) и снимает только по RESET.
- MiSTer и UnrealSpeccy считают комбинаторно: сброс EFF7[2] в 0 сразу возвращает страничность.

**Берём MiSTer/Unreal (комбинаторно), как у нас сейчас.** Аргумент от железа: весь ходовой метод
«отличить 512 от 1024» построен на переворачивании EFF7[2] туда-обратно; с липкой блокировкой Fuse
он бы не работал.

### Р-2. Перезащёлкиваются ли расширенные биты в 128-режиме

- MiSTer морозит их: при EFF7[2] = 1 запись в 7FFD расширенную защёлку не трогает
  (`if(p1024 & ~page_reg_p1024[2]) page_128k <= …`). У нас так же (`memory.v:105`).
- Fuse / Unreal / ZEsarUX держат ОДИН байт 7FFD и маскируют только его ИСПОЛЬЗОВАНИЕ, то есть
  запись в 128-режиме затирает и расширенные веса.

**Берём MiSTer (морозим), но это единственное место, где мы можем разойтись с железом** — см.
раздел 7, тест Т-1. Схемотехнически (одна ИР23 на 8 бит) правдоподобнее вариант Fuse/Unreal.

### Р-3. Дешифрация самого 7FFD

- Velesoft и Fuse требуют A14 = 1: `01xxxxxx xxxxxx0x`, Fuse `{0xc002, 0x4000}` (у Pentagon-128 та
  же строка БЕЗ A14: `0xxxxxxx xxxxxx0x`).
- Таблица Black_Cat для Pentagon-1024SL требует ещё и A0 = 1: `0xxxxxxxxxxxxx01`, а EFF7 —
  `1110xxxxxxxx0xx1`.
- Unreal и MiSTer декодируют мягко: A15 = 0, A1 = 0.

У нас мягко, как у Unreal/MiSTer: `memory.v:96` — `!iorq && !wr && !a[15] && !a[1] && model &&
!page_lock`. **Оставляем мягкое.** Практический эффект различий — только поведение при коротком
`OUT (#FD),A`; софта, который на этом строится, в наших коллекциях не выявлено (см. Т-3).

### Р-4. Порядок весов D6 / D7

Northwood (автор Pentagon-4096) пишет обратное: «Pentagon-1024: #7FFD бит 7 — 256 Кб, бит 6 —
512 Кб, бит 5 — 1024 Кб» ([zx-pk t=28489](https://zx-pk.ru/threads/28489-pentagon-1024-4096-ot-northwood.html),
тот же порядок в [README Pentagon-4096](https://github.com/rdacomp/Pentagon-4096), причём внутри
README он противоречит сам себе в пп. 4.4/4.5). Все остальные источники — включая периодические
«Стандарты памяти» («256K — 6-ой бит #7FFD; 512K — 6 и 7 биты») — за D6 как младший.

**Берём консенсус (D6 младший).** Northwood — одиночное мнение. Практически перестановка D6/D7
переставляет номера банков самосогласованно, поэтому софт, который просто распределяет банки, её не
заметит; заметит только сверка с эталонным эмулятором по конкретному номеру банка.

### Р-5. «Пентагон 1024» — это ДВЕ разные машины

m.d. в том же треде: «Early versions (1.xx) of Pentagon 1024SL have configuration ports mostly like
KAY-1024… D7 = bank 5 ;1024 kB… port 1FFD: D4 = bank 3 ;256 kB, D7 = bank 4 ;512 kB», плюс биты
«protected mode» / «lock», снимаемые только аппаратным сбросом.

**Берём v2.xx (схему с EFF7).** Она и есть то, что все называют «Пентагон 1024». Ветку 1.xx (порт
1FFD в стиле KAY) не реализуем и в меню не показываем.

### Нюанс совместимости с реального железа

На части машин «дополнительные биты порта #7ffd (6,7) подключены параллельно битам порта #dffd
(0,1), чтобы сохранить совместимость с софтом, писанным под Profi 1024» (Alone Coder, там же).
У нас этого нет. Дешёвая опция (десяток LUT), но включать её надо ОПЦИЕЙ машины, а не по умолчанию:
она меняет наблюдаемое поведение #DFFD.

### Первичный аппаратный источник расширения

Схема, Deja Vu #07 (1999), Ivan Mak — <https://zxdn.narod.ru/hardware/dv07pn1m.htm>: «В качестве
портов расширения до 1Mb использованы Profi-порт (#DFFD, mask #07) и Pentagon-1024 (#7FFD,
mask #e7)»; «bit2 порта #EFF7 — это программная блокировка памяти выше 128К». Там же прямым текстом
про 4 МБ: «По аналогичной системе можно подключить и 4Mb-30pin SIMM… **проблема только в реальном
отсутствии порта и софта под такой объем памяти**».

## 3. Память сверх мегабайта («Пентагон 4М»)

### 3.1 Главный вывод: канонического стандарта на 4 МБ НЕ СУЩЕСТВУЕТ

Тред «Разновидности расширения памяти свыше 128к»
(<https://zx-pk.ru/printthread.php?t=4225&pp=40>): «Pentagon + 4Mb Simm (0x7ffd 0x???? 0x????)»
(Максагор — веса прямо неизвестны), «про 4мб на пентагоне не слышал ни разу => для меня такого не
существует» (jtn), «не было слышно о какой-либо программной поддержке этой радости» (Vitamin).

### 3.2 Кандидат A — порт #AFF7 (единственный «именованный»)

Community-документ «Стандарты памяти»: «4096K — используются 5, 6, 7 биты #7FFD + **0,1 биты
#AFF7**» (<https://www.zxby.org/phpBB3/viewtopic.php?t=20>); независимо ZEK (2006): «Pentagon 4096 —
7FFD+AFF7». Ни схемы, ни софта, ни эмулятора с этим портом не найдено. **Реализовывать вслепую
нельзя.**

### 3.3 Кандидат B — склейка чужих портов, и она сама себе противоречит

- rdacomp / Northwood «Pentagon-4096»: «Пентагон + Профи» = 7FFD D6,D7 + DFFD D0..D2 = 4096 КБ;
  «Пентагон + Kay» = 7FFD D5,D6,D7 + 1FFD D4,D7.
- В железе «Пентагон + Профи» реально сделан у Karabas Pro:
  `ram_ext <= port_7ffd_reg(6) & port_7ffd_reg(7) & port_dffd_reg(2 downto 0); -- pent 512 + profi 1024`
  ([karabas_pro.vhd:1384](https://raw.githubusercontent.com/andykarpov/karabas-pro/master/firmware/src/fpga/profi/rtl/karabas_pro.vhd)),
  8 бит страницы = 4 МБ.

**Эти две реализации несовместимы между собой:** у Karabas младшие веса отданы DFFD
(page[5:3] = DFFD[2:0], page[7] = 7FFD[6], page[6] = 7FFD[7]) — сохраняется совместимость с
Profi-1024; у rdacomp наоборот, младшие веса у 7FFD — сохраняется совместимость с Pentagon-512.
Одновременно совместимым быть нельзя. Значит «стандарта» тут нет по определению.

### 3.4 Кандидат C — как поступили НАСТОЯЩИЕ 4-МБ машины

ZX-Evo / TS-Conf вообще не расширяют 7FFD за мегабайт: «PG — Selects page mapped at address #C000.
**Only first 1024kB of RAM available for this paging**»
([tsconf_en.md](https://github.com/tslabs/zx-evo/blob/master/pentevo/docs/TSconf/tsconf_en.md)); всё
сверх — через собственные регистры Page0..Page3. Тот же подход у SpecNext: расширенный режим
включается nextreg 0x8F, а EFF7 описан один в один каноном
(<https://wiki.specnext.dev/Pentagon_1024_paging>).

### 3.5 Решение

**Берём кандидат C.** «Пентагон 4 МБ» не изобретаем:

1. окна 7FFD/DFFD остаются в пределах ПЕРВОГО мегабайта и работают строго по канону §1;
2. память сверх мегабайта адресуется НАШИМ собственным регистром страницы (по образцу Page0..Page3
   TS-Conf), документированным у нас как расширение оболочки, а не как «стандарт Пентагона»;
3. если когда-нибудь понадобится чужой порт ради конкретного софта — брать Profi `#DFFD[2:0]` и
   ЯВНО зафиксировать веса в документе, иначе повторим развилку Karabas ↔ rdacomp;
4. вариант #AFF7 не реализуем, пока не найдётся схема или софт.

### 3.6 Мина в карте памяти (наша, не стандартная)

Расширенные банки живут в DDR по `0x0FE00000` (банки 8..63 = 56 × 16 КБ = 896 КБ, до `0x0FEE0000`),
кадр — `0x0FF00000`, а fs-буфер `FS_BUF = 0x0F900000` занимает 6 МБ ВПЛОТЬ до кадра. То есть
физически между FS_BUF и кадром помещается только текущий мегабайт. **Любое расширение до 4 МБ
требует сначала перепланировать карту DDR**, иначе первое же чтение крупного файла мейлбоксом
затрёт банки. Это работа не по стандарту, а по нашей карте памяти, и делать её надо ПЕРВОЙ.

## 4. ATM Turbo 2+

### 4.1 Источники (три независимых, сходятся по битам)

- Официальное руководство NedoPC «Turbo 2+. Внутренняя архитектура» (2005) —
  [atm2_arch.pdf в живом репо zx-evo](https://github.com/tslabs/zx-evo/blob/master/pentevo/docs/ATM/atm2_arch.pdf).
- Живая RTL ZX-Evolution BaseConf:
  [zports.v](https://github.com/tslabs/zx-evo/blob/master/pentevo/fpga/base/z80/zports.v),
  [atm_pager.v](https://github.com/tslabs/zx-evo/blob/master/pentevo/fpga/base/mem/atm_pager.v),
  [video_modedecode.v](https://github.com/tslabs/zx-evo/blob/master/pentevo/fpga/base/video/video_modedecode.v).
- [MAME src/mame/sinclair/atm.cpp](https://github.com/mamedev/mame/blob/master/src/mame/sinclair/atm.cpp).

### 4.2 Системный порт `out #FF77` (теневой; A0 = A2 = A4 = 1, A3 = A7 = 0)

| Бит | Значение |
|---|---|
| D0..D2 | RG0..RG2 — видеорежим |
| D3 | турбо 7 / 3.5 МГц |
| D5 | Z_I — разрешение прерываний HSYNC |
| D6 | VE1 |
| D7 | VE0 (=1) |

Адресные линии несут отдельные сигналы:

- **A8 = 0 → PEN**: выключение диспетчера памяти, «в каждую четверть ставится страница ПЗУ с BIOS
  CP/M… при включении диспетчер как раз выключен»;
- **A9 = 0 → CPM**: постоянный DOSEN, теневые порты открыты;
- **A14 = 0 → PEN2**: разрешить запись палитры через #FF.

Рекомендованная последовательность руководства: `#4177` открыть теневые, `#0177` + палитра, `#FF77`
закрыть. RTL один в один: `atm_scr_mode<=din[2:0]; atm_turbo<=din[3]; atm_pen<=~a[8];
atm_cpm_n<=a[9]; atm_pen2<=~a[14]` (zports.v:876-880); MAME:123-127 то же.

### 4.3 Диспетчер `out #xxF7` (A0 = A2 = A4 = A7 = 1, A3 = 0)

Окно задаётся A14/A15: `#3FF7 / #7FF7 / #BFF7 / #FFF7` → 0000 / 4000 / 8000 / C000.

- D0..D5 — **инверсный** номер страницы (64 страницы по 16 КБ);
- D6: 1 = ОЗУ, 0 = ПЗУ;
- D7 = 1 → в номер подмешивается #7FFD (у ОЗУ D0..D2 берутся из 7FFD неинверсно; у ПЗУ D0
  подменяется сигналом DOSEN — так и включается TR-DOS по M1 в `#3Dxx`).

Карт памяти ДВЕ, переключает бит D4 (ROM2) порта #7FFD. Подтверждение: MAME
`page = (u16(data & 0xc0) << 8) | u8(~data & 0x3f)`; pentevo `pages[pent1m_ROM] <= ~{2'b11, zd[5:0]}`.

**Конфликт с нашим железом:** окно `#xxF7` перекрывает пентагоновский EFF7 (A15..A12 = 1110,
A3 = 0 — это и есть `#EFF7`, попадающий в маску диспетчера ATM). Обе схемы в одном ядре
уживаются только как ВЗАИМОИСКЛЮЧАЮЩИЕ режимы машины, не одновременно.

### 4.4 #7FFD у ATM

D0..D2 страница, D3 экран 5 (7), D4 ROM2 = быстрая смена карты, D5 lock48. Экран всегда парой
страниц: битовая 5(7) + атрибуты 1(3).

### 4.5 Видеорежимы {RG2, RG1, RG0}

| Код | Режим |
|---|---|
| `011` | ZX 256×192 |
| `010` | аппаратный мультиколор 640×200 (32000 Б; «байт атрибута приходится на один знакоряд — полоску 8×1») |
| `000` | EGA 320×200×16; в байте пара пикселей: левый = D0,D1,D2,D6, правый = D3,D4,D5,D7 |
| `110` | текст 80×25; знакогенератор в ПЗУ, КОИ-8, атрибут INK = D0..D2,D6, PAPER = D3..D5,D7, FLASH нет |

Чётные и нечётные столбцы разнесены по +0x0000 / +0x2000, строки линейны. Остальные комбинации —
технологические экраны, вне стандарта.

**Расхождение Р-6:** ZX-Evolution занял `111` под «текст в одной странице» (`mode_a_txt_1page`) — у
оригинала это неопределённый технологический режим. Туда же `pent_vmode` (16c / мультиколор
Пентагона) — добавка BaseConf, не ATM. **Берём оригинал (2+), добавки BaseConf не тащим.**

### 4.6 Палитра `out #xxFF` при PEN2

16 позиций из 64 цветов, данные **инверсные**, порядок GgRrBb: D4 = G, D7 = g, D1 = R, D6 = r,
D0 = B, D5 = b. Заменяется цвет, который в этот момент на шине (практично — цвет бордюра сразу
после INT; MAME:98-103 подтверждает и инверсию, и «pen = текущий цвет бордюра»). Бордюр 16 цветов:
A3 = 0 → BRD3 = 1, то есть порт `#F6`.

Тот же #FF без PEN2 — системный регистр Beta-диска (DSEL / reset / halt / side). **Это ровно наша
ситуация с SAA1099 на #FF: порт делится по времени.** Правило у нас уже выработано (`MACHINE_CFG
[12:11]` AUTO/ON/OFF, глушить по вставленной странице TR-DOS или живой активности дисковода, а НЕ
по липкой `bdi_session`) — при портировании ATM применять его же.

### 4.7 Что нужно ровно для CP/M

1. После включения PEN = 0 — во всех окнах ПЗУ с BIOS CP/M.
2. Карта «всё ОЗУ» = плоские 64 КБ TPA (рис. 3 руководства: окна = стр. 0, 4, 2, 3), вторая карта
   (ROM2 = 1) держит в окне 0 системную страницу ПЗУ; переключение ОДНИМ `OUT #7FFD` по биту D4.
3. A9 = 0 (CPM) — иначе из ОЗУ до теневых портов не достучаться.
4. Консоль 80×25 + Beta-диск.

HDD у ATM — порт `#FFEF` (A5..A7 = регистры IDE, A8 = защёлка D8..D15). Это **не** наш NEMO, путать
нельзя.

Каноническая раскладка ПЗУ ATM: 0 — BASIC48, 1 — TR-DOS, 2 — BASIC128, 3 — CP/M, и при большем ПЗУ
«данные страницы всегда будут иметь четыре последних номера. Это — стандарт!» (у 64 КБ = #3C..#3F).
У нас раскладка другая (0 = 128-меню, 1 = 48 BASIC, 2 = TR-DOS, 3 = сервисное) — **при портировании
ATM брать ИХ раскладку, свою не навязывать**; наша остаётся у ZX/Пентагона.

### 4.8 ATM Turbo 1: стандарта нет

Официальное описание портов существует только для 2+. По [Википедии](https://ru.wikipedia.org/wiki/ATM_Turbo)
у модели 1 (1991) уже были 320×200, 640×200 и CP/M 2.2, а «свободная страничность любой страницы в
любую четверть», текст 80×25, IDE и 8-канальный АЦП — приобретения 2-й модели. MAME гоняет машину
`atm` (1991) на ТОМ ЖЕ порт-мапе, но помечает её `MACHINE_NOT_WORKING`. **Решение: делать по 2+, про
модель 1 ничего не выдумывать.**

### 4.9 Цена по ресурсам

База — наш собственный замер B0101 (`research/15-pentagon/RESOURCE_SQUEEZE.md:10-15`):
LUT 15554 / 17600 = **88.4 %**, Block RAM Tile 59 / 60 = **98.3 %**, регистры 40 %, DSP 0.
Свободна ОДНА плитка BRAM и ~2000 LUT. Предел — блочная память, а не логика.

**Дёшево:**

| Узел | Оценка |
|---|---|
| Диспетчер (4 окна × 2 карты × ~11 бит) | ~90 триггеров + декодер, ~200-400 LUT |
| Палитра 16×6 в LUTRAM | ~10 LUT |
| Системный порт #FF77 + 16-цветный бордюр | десятки LUT |
| 1 МБ ОЗУ | уже есть (8 банков в BRAM + 8..63 в DDR) |
| 4 страницы ПЗУ с карты | уже есть (16 плиток) — ровно канонический набор ATM |

**Дорого — видео.** Экран 32000 Б читается ОДНОВРЕМЕННО из двух страниц (битовая 5/7 + атрибуты
1/3) на пиксельклоке 14 МГц: 2 байта за 571 нс против 1 байта за 1.14 мкс сейчас, то есть вчетверо
плотнее. Наш отдельный экранный образ `scr_reg` (16К × 8 = 4 плитки) придётся либо удвоить (+4
плитки при ОДНОЙ свободной), либо переделать выборку на второй порт основного ОЗУ. Знакогенератор
2 КБ = 1 × RAMB18 (в свободную плитку влезает). Плюс кадр в DDR: 640×200 4bpp = 320 Б на строку —
новая геометрия у писателя кадра и у масштабатора 720p.

**Скрытая цена.** У ATM любая страница ложится в любое окно, включая `#0000`, поэтому код регулярно
исполняется ИЗ DDR-страниц (у Пентагона так жили только банки 8..63). Путь ожидания DDR становится
горячим на каждом такте, и CDC-правило (нагрузку держать, флаг отдавать на такт-два позже данных)
там обязательно — иначе получим ту же болезнь, которую чинили в B0074.

**Отдельным ядром — реально, но впритык.** Ядра грузятся PCAP, каждому достаётся весь кристалл, и в
ATM-ядро можно не класть General Sound, SAA1099, TurboSound и длинный тейповый FIFO (один FIFO —
4 плитки). Арифметика BRAM: 8 банков ОЗУ (32 плитки) + 4 страницы ПЗУ (16) = 48 из 60 ЕЩЁ ДО экрана,
шрифта, буфера дисковода и буферов оболочки. Сходится только если отказаться от отдельной копии
экрана (читать через второй порт ОЗУ) и урезать тейповый FIFO вдвое.

**Одной строкой:** страничность ATM — копеечная и ложится на то, что у нас уже есть; всё дорогое —
четыре видеорежима, удвоенная выборка из двух страниц на 14 МГц и вторая экранная копия в BRAM, а
BRAM у нас 98.3 %.

## 5. Мультиколор

### 5.1 Стандарт

1. Аппаратного «мультиколора» в ULA НЕТ ни на одной Sinclair-машине. Весь стандарт — одна
   особенность выборки: «the ULA re-reads the attribute information on every pixel row when
   generating the video output; it is possible to write a new value to the relevant memory location
   in between successive lines»
   ([Wikipedia, ZX Spectrum graphic modes](https://en.wikipedia.org/wiki/ZX_Spectrum_graphic_modes)).
   **Порта или бита включения не существует — это гонка процессора с лучом.**
2. **8×1** (hicolour / multicolour / FLI / rainbow): ограничение чисто временное — «the Spectrum's
   processor is not fast enough to write to an entire row of attribute bytes in one scanline, so
   8×1 attributes can only be achieved over 20 columns» (там же). Эталонные движки: BIFROST* =
   18×18 знакомест, BIFROST*2 = 20×22
   ([Spectrum Computing 27405](https://spectrumcomputing.co.uk/index.php?cat=96&id=27405),
   [30003](https://spectrumcomputing.co.uk/entry/30003/ZX-Spectrum/BIFROST*2_ENGINE)).
3. **8×2** (bicolour): «change the row of attributes over the course of two scanlines… can be
   applied to the full width of the screen through the use of the Nirvana+ engine» (Wikipedia);
   Nirvana — «30 columns and 22 rows», «changing color attributes every two scanlines»
   ([irrlichtproject](http://irrlichtproject.blogspot.com/2013/11/bye-bye-8x8-color-grid-nirvana-engine.html)).
   У Saukas есть отдельные сборки под 48 / 128 **и Pentagon** — тайминги в них прошиты, «it is a
   matter of the colours working or not».
4. **Gigascreen** — не режим ULA, а чередование двух экранов по кадрам: 7FFD «Bit 3: Select normal
   (0) or shadow (1) screen… normal screen is in bank 5, whilst the shadow screen is in bank 7»
   ([128K Technical Information, WoS](https://worldofspectrum.org/faq/reference/128kreference.htm));
   «alternated at 50 Hz… in reality the flicker is again too noticeable on CRT» (Wikipedia).
5. **Единственный настоящий аппаратный стандарт 8×1 — Timex SCLD, порт #FF:** D1 = 1 → «Multicolor
   mode: video data at address 16384 and 8×1 color attributes at address 24576»; D1 = D2 = 1 →
   «Extended resolution… even columns from 16384, odd columns from 24576»; D3..D5 — 8 пар ink/paper
   ([Timex I/O ports](https://loadzx.com/timexcomputerworld/timex-io-ports/)). Из клонов —
   TS-Conf/Pentevo: VConfig `VM[1:0]` = ZX / 16c / 256c / text, порт вида `#nnAF`
   ([tsconf_en.md](https://github.com/tslabs/zx-evo/blob/master/pentevo/docs/TSconf/tsconf_en.md)).
6. Требования к видеотракту: атрибут выбирается в свой такт КАЖДОЙ строки (а не раз в знакоместо),
   стабильный INT (позиция и длина) и корректная модель контеншена и длины кадра — у Pentagon
   контеншена нет и кадр 71680 T против 69888, поэтому сборки движков разные. Дополнительной полосы
   памяти не нужно: 8×1 читает те же 32 байта атрибутов на строку.

### 5.2 Наш тракт: 8×1 и 8×2 работают ДАРОМ

7. Захват у нас — пиксельный слепок луча (`sources/fb_capture_rr.v`, параметры FB_W = 384,
   FB_H = 302, 4bpp → DDR), поэтому всё внутрикадровое (8×1, 8×2, BIFROST / Nirvana, бордюр-эффекты)
   ложится без правок RTL.
8. Условие «атрибут на каждой строке» уже выполнено: `sources/atlas_core/video.v:135` —
   `wire attrInputLoad = (h_addr[3:0] == 11 || h_addr[3:0] == 15) && dataEnable;`, цвет собирается в
   `video.v:148-149`.
9. Палитра совпадает точно: 4bpp = 16 цветов RGBI = ровно спектрумовский набор.
10. Полоса: `fb_wr_axi.v:13` — 6795 слов по 64 бит на кадр ≈ 54 КБ, при 50 Гц ~2.7 МБ/с в HP0.
    Мультиколор её не меняет вообще: меняется содержимое, а не объём.

### 5.3 Что реально стоит денег — межкадровые трюки (gigascreen)

11. Шэдоу-экран у нас есть (`bulbulator_zx_ddr_top.v:1061` — `scr_capD`, «shadow-aware»), но выход — 720p50
    (`sources/fb_line_disp.v`, «scanned out at 720p50»), а кадр Пентагона ≈ 48.8-49.4 Гц. Частоты не
    равны, значит кадры периодически дублируются или теряются, и смешение двух экранов будет
    «дышать» с периодом порядка секунды. Это надо ИЗМЕРИТЬ (реальный период кадра ядра против
    HDMI), а не чинить вслепую. Дешёвого решения нет: либо тянуть ядро ровно на 50 Гц, либо
    смешивать два последних кадра в `fb_line_disp` (усреднение 4bpp через палитру → нужен 8bpp
    путь).
12. **Timex-совместимый аппаратный 8×1** (если захочется не гонять процессор): дёшево — декод порта
    #FF, адрес атрибута `0x6000 + строка`, десяток LUT в `video.v`, DDR-тракт не трогается. **Но
    порт #FF у нас уже поделён по времени между SAA1099 и системным регистром Beta-диска** — третий
    претендент требует явной опции машины и того же арбитража, что описан в §4.6.
13. **Что НЕ ложится:** Timex hi-res 512×192 (наш захват 384 px в строке) и ULAplus / 64+ цветов —
    обоим нужен 8bpp или шире буфер, то есть удвоение захвата и своя палитра в `fb_line_disp`
    (механизм там уже есть — NES ходит 8bpp), плюс пересчёт масштаба на 720p.
14. **Вывод: изобретать нечего.** По стандарту у нас уже всё работает для 8×1 и 8×2; проверять надо
    не видеотракт, а тайминги Z80 / INT / контеншена — пентагоновскими сборками BIFROST*2 и
    Nirvana+ как эталонными тестами.

## 7. Чего мы НЕ знаем и обязаны проверить СОФТОМ на железе

Каждый пункт — это место, где источники расходятся или молчат. Проверять на ХОЛОДНОМ старте
(состояние клавиатуры и часть регистров переживает тёплую перезагрузку) и не на глаз, а по дампу.

**Т-1 (главный). Перезащёлкиваются ли расширенные биты в 128-режиме.** Программа: в мегабайтном
режиме выбрать заметный расширенный банк (например 40), записать в окно `0xC000` метку; EFF7[2] = 1;
`OUT (#7FFD), 0`; EFF7[2] = 0; прочитать `0xC000`.
— наша модель и MiSTer: метка на месте (защёлка заморожена);
— Fuse / Unreal / ZEsarUX: банк 0, метки нет.
Эталон — настоящий Пентагон 1024SL v2.x или его владелец на zx-pk. **До закрытия Т-1 менять
`memory.v:105` нельзя.**

**Т-2. Липкость блокировки.** EFF7[2] = 1 → `OUT (#7FFD), 0x20` (bit5 = 1) → EFF7[2] = 0 → пробовать
переключить банк. У нас страничность вернётся. Проверить настоящим детектором объёма памяти (тест
памяти ZX Diagnostics / UMT, любой софт, который печатает «1024K»): если детектор нас видит как
1024 — модель верна.

**Т-3. Строгость декодирования 7FFD (A14, A0) и EFF7 (A0).** Нужен софт, который делает короткий
`OUT (#FD), A` или `OUT (#F7), A`. Проверять надо не гипотезу, а поведение: у нас мягкий декод
поймает лишние адреса. Пока не найден софт, который от этого ломается, — не трогать.

**Т-4. Веса D6/D7 (Р-4).** Самосогласованная перестановка софтом не ловится. Ловится только сверкой
номера банка с эталонным эмулятором на конкретном образе. Нужен эталонный 1024-софт, который
печатает номер банка.

**Т-5. Нужна ли параллель 7FFD[6:7] ↔ DFFD[0:1].** Требует конкретного софта под Profi-1024,
запускаемого на Пентагоне. Пока такого софта в коллекции не выявлено — фича не нужна.

**Т-6. Реальный период кадра ядра против HDMI 720p50.** Нужен для любого межкадрового трюка
(gigascreen, флип 50 Гц). Мерить прибором в RTL, а не глазом: счётчик кадров ядра против счётчика
кадров вывода за фиксированное окно.

**Т-7. Тайминги под мультиколор.** Прогнать пентагоновские сборки BIFROST*2 и Nirvana+. Это тест
INT/контеншена/длины кадра, а не видеотракта. Ожидаемый результат бинарный: цвета либо стоят, либо
рассыпаются.

**Т-8. Порт #AFF7 (Пентагон 4096).** Неизвестно ВСЁ: схема, веса, софт. Не реализовывать. Закрыть
можно только находкой схемы или живого софта.

**Т-9. ATM: точное поведение защёлки палитры.** «Заменяется цвет, который в этот момент на шине»
(руководство) и «pen = текущий цвет бордюра» (MAME) — это одно и то же утверждение с разной
точностью. Для реализации нужен цикл-точный момент выборки; проверяется палитровыми демками ATM.

**Т-10. ATM Turbo 1.** Стандарта нет, MAME помечает машину NOT_WORKING. Не реализовывать.

## 8. Порядок реализации и цена

Расчёт от замера B0101 (`RESOURCE_SQUEEZE.md`): свободно ~2000 LUT и ОДНА плитка BRAM.

| Шаг | Что | Цена ПЛИС | Риск |
|---|---|---|---|
| 0 | **Тесты Т-1, Т-2, Т-7** (софт, без RTL) | 0 | нет. Даёт право трогать `memory.v` осознанно |
| 1 | 1 МБ Пентагона — НЕ ТРОГАТЬ | 0 | совпало с каноном 1:1 |
| 2 | Если Т-1 покажет вариант Fuse — заменить заморозку `page_hi` на общий байт 7FFD с маской ИСПОЛЬЗОВАНИЯ | ~10 LUT | правка одной строки `memory.v:105`, но меняет наблюдаемое поведение |
| 3 | Т-6: прибор «кадры ядра / кадры вывода» | ~40 LUT (два счётчика в отладочный слот) | нет |
| 4 | Timex-совместимый 8×1 (опция машины) | ~10-20 LUT в `video.v` + арбитраж #FF | средний: #FF уже поделён SAA1099 и Beta-диском (§4.6) |
| 5 | Память сверх 1 МБ: сначала ПЕРЕПЛАНИРОВАТЬ карту DDR (FS_BUF ↔ банки ↔ кадр), потом свой регистр страницы в стиле TS-Conf | регистр ~20-40 LUT; карта памяти — работа в прошивке | высокий: мина §3.6, ошибка = fs-буфер затирает банки |
| 6 | Параллель 7FFD[6:7] ↔ DFFD[0:1] опцией | ~10 LUT | низкий, но включать только по Т-5 |
| 7 | Gigascreen (смешение двух кадров) | 8bpp путь в `fb_line_disp` + палитра: сотни LUT, плитки BRAM | высокий, и бессмысленно до Т-6 |
| 8 | **ATM Turbo 2+ — ОТДЕЛЬНОЕ ядро, не режим существующего** | диспетчер + порты + палитра + бордюр ≈ 250-450 LUT; видео — переделка выборки экрана; BRAM: 48/60 занято ещё до экрана и шрифта | самый высокий: BRAM 98.3 %; сходится только без отдельной копии экрана и с урезанным вдвое тейповым FIFO |

Порядок обязателен: шаги 0 и 3 — измерения, они дают основание всему остальному; шаг 5 идёт ПОСЛЕ
перепланировки карты DDR; шаг 8 не начинать, пока не освобождена BRAM (пункт бэклога «буферы
оболочки LUTRAM→BRAM» тут работает в минус — он ЗАНИМАЕТ плитки, освобождая LUT, и с ATM
конфликтует).

Обязательные правила при любом из этих шагов (уже оплачены отказами):

- CDC: нагрузку держать, синхронизировать только флаг, флаг отдавать на такт-два позже данных;
  однотактовый запрос защёлкивать. У ATM это критично — код исполняется из DDR-страниц постоянно.
- Такты ожидания памяти вставлять в `pc3M5` / `nc3M5` (обе фазы), а не в `cpu_ten`.
- Приёмку памяти проходит САМА МАШИНА (пишет и читает Z80, `PUSH` / `LDIR`), а не ARM, и по всем
  восьми байтовым линиям; перед каждым прогоном писать заведомо другой байт (тест без затравки не
  доказывает ничего); банк с кодом теста не затирать.
- После каждой сборки грепать лог на `8-9873` (overwriting previous definition of module) и на
  `has no load` у портов — иначе получим немой узел, как было с SAA1099.
